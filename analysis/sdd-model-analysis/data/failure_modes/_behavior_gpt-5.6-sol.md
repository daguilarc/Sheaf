## Summary of characteristic behaviors

- **Brief-first, near-universal ritual opening.** Almost every session's first 1-2 turns are a scripted announcement of which skills it's invoking (TDD, verification-before-completion, software-principles) before reading the brief and any cited OpenSpec/plan artifacts. Seen in every session read (F/task-8 T1-2, C/task-3 T1-2, C/task-4 T1-2, A/task-1(raster) T1-2, A/task-1(note-msg) T1-2, B/task-1(browser) T1-3). It almost never dives straight into code.
- **Genuine RED is the default, and the model is unusually honest when it can't produce one.** In 6 of 8 sessions the reported RED is a real compiler/runtime failure caused by the missing feature (F/task-8 T9, C/task-3 T6, C/task-4 T8, A/task-1(raster) T5, A/task-1(note-msg) T4, B/task-1(browser) T9). In the two cases where a genuine RED wasn't achievable, the model says so explicitly rather than fabricating one: F/task-5 (dresden) found the behavior already satisfied by inherited edits and only ran a red proof after being pressed by the parent for mutation evidence; B/task-1 (encoder) self-reports `DONE_WITH_CONCERNS` specifically because "no genuine RED occurred."
- **Heavy self-review/audit pass before every commit.** Nearly every session inserts an explicit "contract audit" / "self-review" / "diff audit" turn scanning for scope creep, unchanged public APIs, and untouched unrelated files immediately before staging (C/task-3 T7-T9, C/task-4 T23, A/task-1(raster) T6-7, A/task-1(note-msg) T15, B/task-1(browser) T13-14).
- **Treats scope/authorization boundaries as hard stops, not judgment calls.** When a fix would require touching code outside the task's owned files, it pauses and asks a parent/controller rather than just doing it — C/task-4 (T13-T19, ~4 turns spent awaiting authorization for a shared hot-path change) and B/task-1 (browser) (T3-T6, pauses on an underspecified schema and waits for a controller answer) both block on explicit sign-off.
- **Treats perf/flaky failures with skepticism before accepting them as real.** Rather than reacting to the first red run, it reruns to distinguish transient noise from a reproducible regression: C/task-4 T25-26 (isolated p99 outlier, reruns and gets clean fresh evidence), B/task-1 (encoder) T40-41 (unrelated Braid4 deadline miss, reruns the same binary and the full suite before concluding it was transient).
- **Polling/waiting churn on sub-agents and long shell jobs.** F/task-8 spends roughly 20 of its 42 turns (T17-T36) doing almost nothing but `wait` calls polling a review/build pipeline with short timeouts; C/task-3 similarly burns ~10 turns (T11-T22) polling a spawned `task3_review` agent that repeatedly times out before it responds. This is pure overhead turns, not churn on the actual code.
- **Some large, dense single turns.** Test-authoring turns can be very large — B/task-1 (browser) T7-T9 (4046 + 3620 output tokens designing a full contract suite before any code exists) and F/task-8 T7 (5961 tokens). These are "write the whole test file in one shot" turns rather than incrementally built tests.
- **Occasional leakage of unresolved internal deliberation into the visible response.** In A/task-1 (note-msg) T11, a SAY turn trails into raw uncertain monologue ("...Wait user says full report path likely should write report but exact commit command excludes report... 'Do not edit progress ledg[er]'...") — a rare but real quirk where planning-out-loud isn't fully cleaned up before surfacing.

## Per-session notes

**F — add-browser-wasm-runtime\_\_task-8** (codex-019f4909…). Opens with the standard brief-read/plan-mapping ritual, correctly detects that `em++` is unavailable and pre-commits to reporting `DONE_WITH_CONCERNS` rather than faking a WASM link. Builds one large generic Chrome/Playwright fixture in a cluster of dense turns (T4-T6, several 2000-6000 token turns), hits a real RED (TS type error on a static Node import, T9), fixes it, then hits and fixes a genuine Playwright semantics bug (double-click vs drag ambiguity, T10) and a genuine test-ordering violation (cross-spec-file import banned by Playwright, T15). It finds and correctly declines to fix a pre-existing Task-7/Task-5 test contradiction that falls outside its file ownership (T18-19), escalating instead of quietly patching it. The back half of the session (T17-T36, roughly half the turns) is almost entirely `wait` calls polling a review/build pipeline, several with 15-30s timeouts and empty output — pure waiting overhead rather than productive work. It does incorporate one substantive post-review finding (adding bidirectional sysex coverage to the miniapp smoke, T30) before final commit.

**F — add-dresden-4-synth-app\_\_task-5** (codex-019f5423…). By far the thinnest session in the sample — only 8 turns. It discovers immediately that a shared worktree already contains upstream Task 1-4 edits that appear to satisfy the Task 5 contract, and its default instinct is to write a regression test, watch it pass on the first try, and prepare to report success without ever forcing a real failure ("I'll record that honestly... rather than fabricating a failure," T3). Only after the parent explicitly asks for mutation evidence (T6-7) does it temporarily rip out the just-implemented filter-indicator wiring, confirm the test fails for the right reason, and restore it. This is the one clearest example in the sample of the model's default self-assessment leaning optimistic ("already satisfied") and needing external pressure to get genuine verification — consistent with its F grade.

**C — add-autoscope-density-raster\_\_task-3** (codex-019f5974…). Long, careful session (40 turns) with a fully genuine RED (missing header, exit code 2, T6) and a real 17→28→30 test GREEN progression. Strong self-audit discipline (T7-9: contract audit for scope creep, allocation-free contract, macro-gating). Spawns a dedicated review sub-agent (`task3_review`) and then spends roughly 10 turns (T11-T22) polling it with repeated timeouts, an interrupt, and a followup nudge before it responds — a clear instance of coordination/polling churn. The review is substantive, though: it surfaces two real hysteresis/threshold edge cases (T24), which the model fixes with new focused regressions rather than just patching code. After the primary commit it accepts a second, unprompted "efficiency fix" pass (T34-40) — its own initiative to preallocate a scratch buffer — again driven by full RED→GREEN plus ASan/UBSan re-verification, showing it treats post-commit review feedback as a reason to reopen the TDD loop rather than bolt on a patch.

**C — add-standard-modulators\_\_task-4** (codex-019f68f8…). Establishes a numeric performance baseline before touching code (T5: current deadline averages recorded). Writes a large test suite in one dense turn (T7, 7655 tokens) covering topology/lifecycle/ownership, gets a real RED (T8), reaches GREEN (T10), but then discovers a genuine 96kHz deadline regression (T11) and applies systematic-debugging discipline: isolates the cause with a temporary single-variable diagnostic that it explicitly restores immediately after (T12), rather than leaving speculative code in place. When the fix requires touching a shared hot path outside its file ownership, it stops and explicitly asks the parent for authorization (T13-19, spending real turns waiting) instead of just doing it. After authorization, it adds new characterization tests for the sparse-modulation edge cases before implementing the optimization (T20-21) — a correct RED-first sequence even for a perf-motivated change. It treats one isolated p99 outlier as suspect rather than a real failure and reruns for fresh evidence before committing (T25-26). A second work block after a context compaction (T29-39) responds to review feedback by adding a missed lifecycle regression (bulk-clear vs. explicit-null-assign) rather than assuming the original test already covered it.

**A — add-autoscope-density-raster\_\_task-1** (codex-019f595c…). The cleanest, most economical session in the sample — 9 turns, no wasted polling, no churn. It reads the brief and, on its own initiative, decides the brief's suggested two-assertion RED is too narrow and expands it to the full behavioral contract before the first build (T4), producing a genuinely comprehensive RED (T5). GREEN is reached in one implementation pass (T5-6), followed by a self-driven refinement (double→float normalization ordering, `noexcept` signature pinning) purely from its own review, not external feedback (T6). Verification, staged-file audit, and commit all happen in single well-scoped turns. This session is a good baseline for what an efficient, well-disciplined run looks like: brief → full RED → GREEN → self-refine → verify → commit, no dead turns.

**A — add-note-system-message-mappings\_\_task-1** (codex-019f6ebb…). Two clean RED→GREEN cycles run in sequence rather than one big one: a first slice (processor typed encoder/press-release) gets its own RED (T4) and GREEN (T5-6), then a second slice (persistence/validation/feedback-suppression) gets an independent RED (T8-9) and GREEN (T10-11) before either is merged into a final verification pass. This incremental-slice structure is more granular than most other sampled sessions, which tend to write one large test file per task. Turn 11 contains a distinctive quirk: unresolved internal deliberation about whether the report file should be part of the commit leaks directly into the visible SAY text ("...Wait user says full report path likely should write report but exact commit command excludes report... 'Do not edit progress ledg[er]'..."), suggesting the reasoning-to-communication boundary isn't always cleanly enforced. Despite that, self-review (T15) and final verification/commit are executed correctly and the task is graded A.

**B — fix-browser-native-audio-and-generic-app-packaging\_\_task-1** (codex-019f78eb…). Notable for pausing on ambiguity rather than guessing: it identifies that the approved design artifacts don't fully specify several contract field shapes and explicitly asks the controller before writing any tests (T3-6), waiting through one timeout before getting an answer. Once unblocked, it authors two large test suites in dense, low-narration turns (T7-9, catalog: 4046 + 3620 tokens; T11-12, ABI/browser-facade) — each preceded by a real RED (T9: missing compiled JS artifact; T12: undeclared C exports plus `undefined` facade versions) and each reaching a genuine GREEN. It runs a deliberate compatibility audit afterward (T14) to catch collateral fixture breakage from making a field mandatory, updating 11 affected mock facades rather than treating the new feature as isolated. Final staging/diff review and commit are handled in a single controlled pass (T17-19) with explicit accounting of excluded unrelated files.

**B — synchronize-absolute-encoder-feedback\_\_task-1** (codex-019f6bd7…, internal label "task-5"). This session is unusual in the sample: most of its turns (T1-33) are actually collaborative OpenSpec proposal/design dialogue with the user — proposing a weighted-projection math scheme, iterating on an epoch-based feedback-loop design across several user corrections, and researching the real MIDI Fighter Twister channel semantics rather than assuming its own prior claim was right (T21 gets corrected by the user in T22, and it goes back to the manual in T25-26 rather than defending the earlier answer). The actual implementation-verification portion only starts at T34. There, it explicitly flags that its two new end-to-end tests passed against the unmodified implementation ("characterization coverage rather than a behavioral RED," T37) and reports `DONE_WITH_CONCERNS` for that reason alone even though every check ultimately passed — again showing the model surfacing a missing true-RED rather than silently accepting a pass. It also correctly treats an unrelated `braid4_deadline_tests` failure as needing a rerun before deciding whether it's real (T40-41), consistent with the perf-skepticism pattern seen in the C-graded sessions.
