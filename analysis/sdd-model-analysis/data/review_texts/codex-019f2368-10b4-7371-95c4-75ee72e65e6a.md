### Spec Compliance
Partially compliant. The UI, device enumeration/open/close/status, endpoint persistence wiring, MIDI input tagging, sender start/stop ordering, and include/synth immutability are mostly covered. However, the port misses old-app processor-swap safety and output reset parity.

### Strengths
- `MidiPanel` implements the requested controls and absent-device reopen behavior.
- `MidiHandlers.hpp` is correctly left unchanged; tagging is added in the forwarding path.
- `Runtime` wires the rebuild callback before `Initialize()`.
- Sender shutdown ordering is correct: `Stop()` before closing the output device.

### Issues
#### Critical (Must Fix)
- Processor-swap race / possible UAF: `MidiPanel.hpp:49-54` dereferences `inputTarget_` without synchronization, while `ReopenPersistedEndpoints()` writes it at `MidiPanel.hpp:153-154`. Worse, `Engine::MessageThreadTick()` destroys/replaces `midiProcessors_` at `Engine.hpp:264-268` before invoking the callback that updates `inputTarget_`. An incoming MIDI callback can therefore call through a stale pointer to the destroyed old input processor. The old app avoided this by `SetProcessor(nullptr)` before replacing `midiProfile_`, protected by `MidiInHandler`’s mutex (`Main.cpp:335-339`, `MidiHandlers.hpp:29-31`, `85-93`).

#### Important (Should Fix)
- Missing output `Reset()` regresses visible MIDI controller sync. The old app reset every output processor after manual open and saved-device reopen (`Main.cpp:379-383`, `420-424`). Those resets clear output caches (`MidiController.cpp:634-667`, `813-850`), forcing a full LED/value resend. The new code opens outputs at `MidiPanel.hpp:239-240` and `165-167` without resetting, while `Engine::MessageThreadTick()` keeps processing output caches even when the physical output is closed (`Engine.hpp:272-273`). Result: opening/reopening an output can leave hardware stale until each control changes.

#### Minor (Nice to Have)
- The unconditional post-`Initialize()` `ReopenPersistedEndpoints()` is directionally correct for the silent first rebuild, and it does not double-open because it closes first. It does cause redundant close/reopen if the startup-patch callback already opened devices, but that is acceptable once the processor lifetime race is fixed.

### Assessment
**Task quality:** Needs fixes
**Reasoning:** The implementation covers much of the requested surface, but the input forwarding pointer can race with engine processor rebuilds and become dangling, which is a correctness blocker. The missing output reset is also a real old-app parity regression with user-visible stale hardware state.
