**Minor — untested reliance on default-initialization for fail-closed behavior on read failure**
`projects/synth/apps/miniapp/MiniAppUI.hpp:100-106`
`ReadGangedRandomLfoSnapshotFromCore` returns `bool` (`MiniAppUiModel.hpp:269-274`), but the call site discards it. On a failed read (`ReadSnapshot` retries exhausted, `DspRandomLfo.hpp:230-235`), the output param is left untouched, so the panel renders whatever `gangedRandomLfoSnapshot` held before the call. This currently works correctly only because the variable is freshly default-constructed (`sampleRate = 0.0`, `DspRandomLfo.hpp:151`) on the stack every frame, which `BuildGangedRandomLfoCommands` treats as invalid and fails closed to background/axis-only (`GangedRandomLfoVisualizer.hpp:169-174`). The sibling retained visualizer (`GangedRandomLfoVisualizer.hpp:257-262`) does this defensively and explicitly (`if (!ReadSnapshot(...)) snapshot.sampleRate = 0.0;`); the new direct-build path gets the same outcome only implicitly, and no test pins this invariant down for this call site. It's correct today, but a later refactor (e.g., caching the snapshot in a member instead of a per-frame local, for performance) would silently reintroduce stale-frame rendering with nothing to catch it.

**Minor — hardcoded voice count duplicates a named constant**
`projects/synth/apps/miniapp/MiniAppDraw.hpp:47-48`
`BuildGangedRandomLfoPanelCommands` takes `synth::GangedRandomLfoSnapshot<2>` as a literal, while `MiniAppUiModel.hpp:266-267` defines `MiniAppGangedRandomLfoSnapshot` off `MiniAppCore::kVoiceCount`. The two are consistent today only because `kVoiceCount == 2` (`MiniAppCore.hpp:40`). Not a live bug — a mismatch would be a compile error, not a silent failure — but using `MiniAppCore::kVoiceCount` here would remove the duplicated magic number.
