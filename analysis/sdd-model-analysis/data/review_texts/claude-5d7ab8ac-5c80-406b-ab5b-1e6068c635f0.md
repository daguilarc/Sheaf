I've reviewed the diff package and fix report against both original Important issues.

### Strengths

- **Issue 1 (realtime allocation) is genuinely fixed.** `HostState` now owns a `synth::BasicMidi midiScratch` whose `raw` vector is `reserve(3)`'d in the constructor. `DrainMidiInput` reuses it via `raw.clear()` + `raw.insert(...)` for ≤3 bytes. `clear()` preserves capacity and the reserved capacity (≥3) is never exceeded, so the insert cannot reallocate. The old per-message `std::vector` construct/reserve/push/move is gone, and `<vector>` was dropped from the includes.
- **Issue 2 (read mutates state) is genuinely fixed.** Frame construction moved into `RefreshUiFrame`, called only from create / message_tick / dispatch_action. `sheath_browser_ui_frame()` now returns the cached frame, keeps `frameVersion` stable on repeated reads (the `frameVersion == 0` branch is lazy-init only), and consumes the dirty signal by clearing `uiFrameDirty`. `sheath_browser_ui_dirty()` returns the real cached flag instead of hard-coded `1`.
- **Both tests are meaningful and target the exact regressions.** The allocation test warms `process()` once *before* enqueuing MIDI, then counts global `operator new` calls only across the draining `process()` call and asserts zero — a correct realtime guard that isolates the MIDI-drain path. The UI-frame test verifies version stability across repeated reads, dirty consumption on read, and version-advance + dirty-set on tick.
- Shutdown correctly resets the new state (`uiFrameDirty`, `midiScratch.timestamp/raw`).

#### Minor (Nice to Have)
- **`SerializedFrame::header.dirty` is always serialized as `1`.** `RefreshUiFrame` always passes `true` to `SerializeFrame`, so the in-frame header dirty flag is decoupled from the consumable ABI-level `sheath_browser_ui_dirty()`. The test even asserts `firstFrame->header.dirty == 1` after a read that has already cleared `sheath_browser_ui_dirty()`. Not a bug (JS-side skip logic uses `ui_dirty()`/version), but the two "dirty" notions are worth a comment or reconciliation.
- **`dispatch_action` refreshes the frame without applying the action.** The built `ActionMessage` is still discarded (pre-existing), yet `RefreshUiFrame` now runs after it. Harmless here and out of scope, but it means a dispatch bumps the version without any state change.
- **Coverage gaps:** the UI-frame test doesn't assert `dispatch_action` refreshes the cache, nor that audio `process()` leaves the frame version untouched. Both would tighten the regression net.
