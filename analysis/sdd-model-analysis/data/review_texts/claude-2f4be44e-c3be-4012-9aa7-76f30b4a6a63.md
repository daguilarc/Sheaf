### Important

**1. Sidebar/Back page navigation is no longer synchronous — it now lags by up to one UI timer tick, and no test would catch a regression here.**

- `projects/synth/include/synth/RuntimeMainComponent.hpp:402-425` (`HandleSidebarAction`/`ReturnToApplication`) only mutate `currentPage_`. Neither this code nor `RuntimeMainComponent::DispatchAction` (`RuntimeMainComponent.hpp:130-157`) triggers any JUCE-side re-render — `actionHandler_` is never wired up by `MainPane` (nothing calls `mainComponent_.SetActionHandler(...)`).
- `projects/synth/runtime/MainPane.hpp:39-43` — `MainPane::ShowPage(Page)`, the wrapper that *does* call `renderer_.RefreshFromSurface()` synchronously, is dead in production: real sidebar/back clicks flow `SemanticTextButton::onClick` → `PortableComponent::DispatchBackendAction` → `RuntimeMainComponent::DispatchAction` → `HandleSidebarAction`/`ReturnToApplication`, never through `MainPane::ShowPage`.
- Previously (code deleted by this diff, old `MainPane.hpp:839-852`), `sidebar_.onAction` called `MainPane::ShowPage()` directly, which synchronously did `setVisible`/`resized()` — an instantaneous switch. The removed doc comment even called this "binding": pages toggled via `setVisible`, driven straight from the click handler.
- The same pattern applies to the Audio-status hook: old `AudioPageHost::SetStatus` (`projects/synth/juce/RuntimePagesJuce.hpp:151-155`) called `m_renderer.RefreshFromSurface()` immediately when the runtime pushed new status text. The new `JuceRuntimeMainServices::runtime_.SetAudioStatusHook` (`JuceRuntimeMainServices.hpp:24-26`) only caches `audioStatus_`; it's applied lazily inside `RefreshAudio()` (`JuceRuntimeMainServices.hpp:123-126`), which only runs from the next tick's `RuntimeMainComponent::Refresh()`.
- Net effect: clicking Audio/Controllers/File/Back, or an async audio-status push, now waits for the next `ShellComponent::RepaintAll()` → `MainPane::RefreshOnTick()` (bounded by `App::Config().uiFrameHz`, default 30 Hz ≈ 33 ms — see `Runtime.hpp:296`) before the visible UI updates, instead of updating in the same frame as the click.
- `RuntimeShellSessionTests.cpp:474-486` masks this: it explicitly calls `.GetMainPane().RefreshOnTick()` right after `onClick()`, so the test can't detect if this synchronous-refresh step were missing or reordered.
- Impact in practice is likely a single frame of visible lag (not a functional break), but it's an unremarked, untested regression from a previously "binding" synchronous contract, worth an explicit decision (accept the lag, or wire `mainComponent_.SetActionHandler` to call `renderer_.RefreshFromSurface()` after every dispatch).

### Minor

**2. `JuceRuntimeMainServices::controllersSurface_` is never nulled out when the object it points to is destroyed.**
- `JuceRuntimeMainServices.hpp:227` (`controllersSurface_`) is set in `RefreshControllers` (`JuceRuntimeMainServices.hpp:193-204`) to `&surface`, where `surface` is `RuntimeMainComponent::controllersSurface_` — a member owned by `mainComponent_`.
- `MainPane`'s member order (`MainPane.hpp:98-101`: `runtime_`, `services_`, `mainComponent_`, `renderer_`) destructs in reverse: `renderer_`, then `mainComponent_` (which destroys the pointed-to `ControllersPageSurface`), then `services_` — whose destructor (`JuceRuntimeMainServices.hpp:37-42`) is what actually clears the MIDI-rebuilt hook (`JuceRuntimeMainServices.hpp:28-34`) that dereferences `controllersSurface_`.
- Between `mainComponent_`'s destruction and `services_`'s destruction, `controllersSurface_` is dangling and unguarded. I could not find a live call path that fires the MIDI-rebuilt hook in that window — `Engine::EditInstrument`/`RebuildMidiProcessors` invocations are message-thread-only and synchronous, and nothing in the intervening plain destructor calls re-enters the message loop — so this appears unreachable today. Flagging as a fragile invariant rather than a confirmed bug: worth defensively nulling `controllersSurface_` (or clearing the hook before `mainComponent_` is torn down) so a future refactor can't silently reintroduce a UAF.

**3. `audioSyncPending_` is dead, write-only state.**
- Set `true` by `runtime_.SetAudioSyncHook([this] { audioSyncPending_ = true; })` (`JuceRuntimeMainServices.hpp:27`), unconditionally reset to `false` at the end of every `RefreshAudio()` call (`JuceRuntimeMainServices.hpp:127`), and never read anywhere else. It has zero effect on behavior — harmless only because `RefreshAudio()` unconditionally recomputes device names/options/selection every tick anyway (a strict superset of what the old `AudioPageHost::Refresh()`-on-sync did). Should be removed, or actually wired to something, rather than left as a misleading vestige of the old sync-driven pattern.

**4. Test gap: the new per-root filtering in `AutoLayoutStartY` is unexercised.**
- `PortableJuceBackend.hpp:466-485` now filters draw-node bottoms by `m_nearestRootByNodeId[node] == rootId` before folding them into a root's auto-layout start Y. The new composite test (`PortableJuceBackendTests.cpp:312-343`) uses 12 plain buttons with no `Draw` node at all, and the wide-draw shell test (`RuntimeShellSessionTests.cpp:492-501`) has a single explicit-bounds `Draw` node with nothing unbounded after it in that root. No test has a nested root containing both a `Draw` node and a trailing unbounded control, alongside a sibling root's own `Draw` node — i.e., nothing would fail if the `rootIt->second != rootId` filter were removed or inverted.

**5. Navigating to Audio/File/Controllers now destroys (not just hides) the app's JUCE-side UI state.**
- `RuntimeMainComponent::BuildTree()` (`RuntimeMainComponent.hpp:91-123`) returns either the app's tree or the current runtime-page's tree, never both. `PortableComponent::RebuildControls()` treats nodes absent from the new tree as removed (`PortableJuceBackend.hpp:608-623`), so switching away from `Page::None` now tears down all of the app's JUCE controls rather than merely `setVisible(false)`-ing them, as the deleted `MainPane.hpp` doc comment explicitly called "binding" ("never destroys/reconstructs the app component"). Confirmed the App's own logical/audio state is unaffected (`RuntimeShellSessionTests.cpp:489-490` checks `AppSurface()` identity survives), but any purely-JUCE ephemeral state (in-progress `TextField` edit, open `ComboBox`, scroll position, an active pointer-drag) is now lost on page navigation. This is a direct consequence of Task 1's already-approved `RuntimeMainComponent` contract (one tree at a time), not something Task 2 could avoid while implementing that concept faithfully — noting for awareness rather than as an actionable Task 2 defect.

**6. CoreMIDI diagnostic is not actionable.**
- No code touched by this diff (`PortableJuceBackend.hpp`, `JuceRuntimeMainServices.hpp`, `MainPane.hpp`, `Shell.hpp`) opens or negotiates MIDI devices — `MidiConnectionManager.hpp` is unmodified. `CoreMIDI error: 580 - 10000003` is JUCE's own device-manager complaining about the sandbox having no real MIDI service/hardware; it appears identically in RED and GREEN runs and doesn't affect any exit code. No regression indicated.
