## Review: Task 1 — Native browser audio callback restoration

I read the brief, the report, and the full 2,635-line diff, and cross-checked the changed source against the current tree (no tests rerun). Findings first, then verdicts.

### Findings

All findings are **LOW** / advisory. I found no correctness defect in the changed lines and no spec deviation that blocks acceptance.

**1. LOW — `createWorkerRuntimeClient` is now a silent audio dead-end** · `src/main.ts:105-133`, activation cliff at `src/main.ts:189`
The worker client no longer exposes `startAudioWorklet` (correct per the brief — `AudioContext` can't be cloned into a worker). But the consequence is a sharp cliff: any consumer that builds a worker client *and* has an activation lease reaches `AudioBridge` → `native-audio-worklet-required` → `throw "audio activation failed"`. Production is safe because `installSynthBrowserApp` defaults to `createDirectRuntimeClient` (`main.ts:287-288`) and the launcher passes `runtimeClientFactory` through unchanged, so the leased context flows to the direct client. This is spec-intended, not a bug — worth a one-line comment on `createWorkerRuntimeClient` noting audio is unsupported there, so a future caller isn't surprised.

**2. LOW — async `stop()` weakens unload-time teardown for the worker path** · `src/main.ts:219-224`
`finishStop` now `await`s `runtime.terminate?.()`, and the worker client's `terminate` awaits a `{type:"destroy"}` round-trip before `worker.terminate()`. Fired from `pagehide`/`beforeunload` via `void this.stop()`, that round-trip may not settle before the page freezes (the old code terminated the worker synchronously). For the direct client the destroy is a resolved-promise chain that runs as microtasks, so the shipped path is fine; only the worker path regresses, and only on hard unload where the OS reclaims anyway. Acceptable, noting for completeness.

**3. LOW — the "finite deadline" progress gate is effectively a no-op** · `src/worker.ts:347`
`Number.isFinite(stats.deadlineMicrounits)` can never be false for the real runtime: `deadlineMicrounits` originates from `_synth_browser_audio_worklet_deadline_microunits` (a `std::uint32_t`), so it's always a finite integer. The meaningful part of the gate is `stats.blocks > initialBlocks`. This satisfies the brief's Step 7 wording literally but the deadline check adds no real protection. Fine to leave; just don't read it as "deadline health is verified."

**4. LOW — minor coverage gaps on new failure branches** · `src/worker.ts:198`, `src/audio.ts:20`
Two new error branches aren't exercised: `emscriptenRuntimeFacade.startAudioWorklet` throwing "failed to register AudioContext" when `emscriptenRegisterAudioObject` returns `0` for a supplied context, and the `audio-bridge-stopped` diagnostic (start after shutdown). The happy paths and `native-audio-worklet-required` are covered. Non-blocking.

**5. LOW — native worklet-thread lifetime vs. `context.close()` rests on unchanged code** · `BrowserRuntime.hpp` (destructor not in diff)
Teardown order is runtime-destroy → `context.close()` → package dispose, asserted by `miniapp-smoke.spec.ts`. Safety depends on `synth_browser_destroy` stopping/joining the Wasm AudioWorklet thread (which holds `this` as callback userData) *before* the leased context closes. That destructor isn't in this diff, and the adopted context is now the launcher-owned JS context rather than a runtime-created one. The passing teardown-order smoke test gives real evidence, but this is the one place I'd want a maintainer to confirm the destructor joins the worklet thread rather than relying on `context.close()` to quiesce it.
