### Findings (by severity)

**1. Medium — Makefile omits `EXPORTED_RUNTIME_METHODS`; `stringToUTF8`/`lengthBytesUTF8` will be undefined at runtime**
`Makefile` (both `fake_browser_app.js` and `miniapp.js` targets)

`worker.ts:withUtf8` (lines 366–374) calls `module.lengthBytesUTF8(...)` and `module.stringToUTF8(...)`, and `emscriptenRuntimeFacade` reaches into `module.HEAPU8`. The `em++` command only passes `-sEXPORTED_FUNCTIONS='[...]'` (which correctly covers `_malloc`, `_free`, and the eight `_synth_browser_*` symbols) but has **no `-sEXPORTED_RUNTIME_METHODS`**. In modern Emscripten under `-O2`, `stringToUTF8` and `lengthBytesUTF8` are dead-code-eliminated unless explicitly exported, so `module.lengthBytesUTF8` is `undefined` and every `initialize` / `dispatch-action` (the two string-passing ABI calls) throws `TypeError` at runtime.

This is invisible today because (a) `em++` isn't installed, so no WASM artifact was produced, and (b) `runtime-core.spec.ts` injects a plain-object fake facade, so `withUtf8`/`emscriptenRuntimeFacade` are never executed. Fix: add `-sEXPORTED_RUNTIME_METHODS='["stringToUTF8","lengthBytesUTF8","HEAPU8"]'` (HEAPU8 is usually attached, but list it to be safe) to both targets. I'd treat this as required before the WASM path is considered working, but it's correctly out of the *tested* surface for this task.

**2. Low — `check:generic-runtime` guard fails open if `rg` is absent**
`package.json:9`

`"! rg -n '...' src ../include/synth/browser cpp --glob '!cpp/miniapp_entry.cpp'"` — when a match is found, `rg` exits 0 → `!` → fail (correct); no match, exit 1 → pass (correct). But if ripgrep isn't installed, `rg` exits 127 → `! 127` → **0 (pass)**, so the no-app-branch guard silently succeeds without scanning anything. It also hard-depends on `rg` being present in whatever CI runs `npm test`. `rg` is present in this dev box (15.1.0), so it works here; consider `grep -rE` or asserting `rg` exists, so the guard can't pass vacuously.

**3. Info — worker `process` hardcodes null outputs**
`worker.ts:381` passes `0` for the `outputs` pointer to `_synth_browser_process`. This is the expected output-only placeholder (the real audio-buffer bridge is a later task), but note that as written `process` can never render into a real buffer, and against a real module it would forward `outputs=null` into `Runtime::Process` → `engine_.ProcessBlock` with a null output array. Fine for this task's scope; flagging so it isn't forgotten when the audio bridge lands.

**4. Nit — double `RuntimeFor()` evaluation**
`BrowserRuntimeAbi.cpp` — each ABI shim evaluates `RuntimeFor(runtime)` twice (`X == nullptr ? ... : X->...`). Harmless (a reinterpret_cast), just slightly noisy.
