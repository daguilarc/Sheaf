### Spec Compliance
Mostly compliant, but the post-Init bypass is not actually closed.

### Strengths
The steady-state empty patch bus path stays lock-free. `DrainPatchInputBus()` only takes the mutex after `Pop()` succeeds.

The runtime output selector now uses `AudioDeviceSnapshot()` plus `SetAudioDeviceFromHost()`, and the new regression test proves host-select-then-revert fires the previously missed callback.

The input combo is no longer dead: it has selection sync, `onChange`, runtime wiring, state persistence, and setup application.

### Issues
#### Critical (Must Fix)
`AppContext::audioDeviceState` remains a public raw mutable pointer to `Engine::audioDeviceState_` via `Engine::Context()` (`Engine.hpp:83`, `Engine.hpp:402`, `AppContext.hpp:61`). Removing `AudioDevice()` does not close the post-Init bypass: any app that retained the init context, or any host code with `engine.Context()`, can still mutate the live state without the mutex and without advancing `lastNotifiedAudioDeviceState_`, recreating the stale-shadow/data-race class this fix is meant to eliminate.

#### Important (Should Fix)
`ApplyPendingPatchMessages()` still passes `audioDeviceState_` directly into `ApplyPatchMessage()` without holding `audioDeviceStateMutex_` (`Engine.hpp:664-678`). This is pre-audio and not currently a runtime race, but it contradicts the stated invariant that patch-message application touches the state pair under the lock.

#### Minor (Nice to Have)
Patch-driven input-device changes are not applied symmetrically: `OnEngineAudioDeviceChanged()` reads only `outputDeviceName`, so a patch that changes only `inputDeviceName` can sync the combo to a state the JUCE setup did not apply.

### Assessment
**Task quality:** Needs fixes
**Reasoning:** The main runtime UI path is fixed, and the tests cover the missed callback, but the raw `AppContext` pointer leaves a post-Init unlocked mutation path into the same guarded state.
