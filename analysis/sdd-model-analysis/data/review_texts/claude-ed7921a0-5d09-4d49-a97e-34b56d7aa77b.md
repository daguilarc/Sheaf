**Critical**

1. Matrix feedback delay is two internal samples, not the required one, and no test catches it — `projects/synth/apps/dresden-4/Dresden4Core.hpp:222-244`, specifically line 230 (`matrixModule_.Inputs() = delayedOscillatorOutputs_;`) and lines 235-238 (`delayedOscillatorOutputs_[oscIx] = dresdenModule_.OscillatorOutput(oscIx);` set *after* matrix processing, for use by the *next* subframe).
   Tracing `ProcessInternalSubframe` across subframes m-1, m, m+1: `delayedOscillatorOutputs_` holds subframe m-1's VCO output when matrix runs at subframe m, so `rawMatrixOutputs_`/`normalizedMatrixSources_` computed at subframe m are a function of O_{m-1}, not O_m. Those normalized values are then only consumed by `quadGroup_->UpdateModValues()` at subframe m+1 (confirmed via `src/ParameterModulation.cpp:611-613` and `:384-396`, a plain unsmoothed copy). Net effect: an oscillator sample at subframe k first influences a later oscillator sample only at subframe k+2 — a two-sample round trip.
   OpenSpec `synth-dresden-4/spec.md:63-70` (d4-3 body + "Matrix receives post-gain oscillator outputs" scenario) and `:168-170,187-190` (d4-7 "One-sample delay uses internal time": "matrix feedback reaches parameter evaluation after exactly one internal sample") describe VCO output feeding the matrix in the *same* subframe, with the single one-sample delay occurring only between matrix-output publish and modulator consumption. The implementation instead adds an extra buffering stage between VCO and matrix input, doubling the loop delay. This matches `task-5-brief.md:84`'s ("matrix consumes the previous internal subframe's post-gain VCO outputs") wording, but that brief phrasing itself conflicts with the OpenSpec spec text, which is the authoritative acceptance contract per the review scope. `task-5-report.md:30,92-93` asserts "one-internal-sample delayed matrix feedback" as satisfied, which is not accurate against the spec's definition.
   No test exercises this: `matrix_sources_materialize_quad_modulator_values_for_four_voices` (`dresden4_system_tests.cpp:164-186`) bypasses `ProcessInternalSubframe` entirely via `SetRawMatrixOutputForTest`/`PublishMatrixModulatorsForTest`, so the actual delay chain through `ProcessBlock` is never verified.

**Important**

2. `BipolarMatrixMixerModule` default parameter color was changed from Grey to Red globally, not scoped to Dresden — `projects/synth/include/synth/Modules.hpp:292` (was `Color::Grey`). This module is documented as a generic reusable primitive independent of Dresden (`openspec/changes/add-dresden-4-synth-app/specs/synth-modules/spec.md:39`, `design.md:15`), while the red-parameter requirement is Dresden-specific (`synth-dresden-4/spec.md:38`, d4-2). The codebase already has the correct pattern for this exact situation — per-instance `SetColor(voiceIx, Color)` overrides used for `Dresden4VcoModule`/other voice modules (`Modules.hpp:178-182,617-621`, exercised in `Dresden4Core.hpp:104-108`) — but no equivalent override exists on `BipolarMatrixMixerModule`, so the only way to satisfy Dresden's red requirement was to mutate the shared default for every current and future consumer. No test asserts the module's default color either way (confirmed: no `Color::Grey`/`Color::Red` assertions in `module_tests.cpp` for the matrix cases), so this is an unguarded, silent layering violation — self-acknowledged as "intentionally broad" in `task-5-report.md:100`.
