## Verdict: **APPROVE WITH MINORS**

The implementation correctly realizes the intended behavior across all four tasks. Parameter target recompute cadence is now app-owned via `ParameterGroupConfig::targetComputeIntervalSamples` (default 16, positive-validated); `Parameter::ProcessSample`/`ParameterGroup::ProcessSample` recompute at `sampleIndex % interval == 0` then `ProcessLite`; the engine exposes `AudioBlock::startSample` and no longer calls `ComputeAllTargets()` in the steady-state pump; and the miniapp/rig/module callers migrated to group-level per-sample processing at `block.startSample + frame`. OpenSpec tasks 1.1–4.3 are all marked `[x]`, and the task-4 report shows the full `make test` at exit 0 plus strict validation passing.

### Correctness verification (no blocking issues found)
- **`ComputeAllTargets` removal is scoped correctly** (`Engine.hpp:264` area): the once-per-block call is gone; `ComputeAllTargets()` survives only as a declaration and for non-steady-state callers. `block.startSample` is set from the pre-increment `fetch_add` return, so consecutive blocks expose monotonic absolute sample positions.
- **Group coverage equivalence**: old `ComputeAllTargets()` computed every manager parameter; new `ParameterGroup::ProcessSample` iterates top-level params and relies on `Parameter::Compute`'s recursion for modulation-depth children. For the single-group miniapp this is behaviorally equivalent, and `parameter_group_process_sample_covers_top_level_and_modulation_depth_targets` proves depth targets refresh (`ParameterModulation.cpp:572-577`).
- **`parameters_` in MiniAppCore is not dead** — still populated and read by `Parameters()` accessor (asserted `== 12` in system tests). Not a finding.
- **One-sample modulation delay preserved**: module order (params → VCO → filter → LFO → `UpdateModValues` → output/scope) is unchanged; the delay is formalized by cached-knob reads in `ProcessLite`.

### Minor findings

**M1 — Stale doc comment (documentation contradicts the new contract).** `projects/synth/include/synth/AppConcepts.hpp:30-36`
The `HasProcessFrame` concept still documents the hook as running *"after `ComputeAllTargets()` (so it observes post-message-drain, freshly-computed target state)"*. The design explicitly required the `ProcessFrame()` contract to stop being documented as observing freshly-computed targets. The parallel comment in `Engine.hpp` and the `ProcessFrameApp` test were both updated (now "after message drains"), but this concept header was missed. Documentation-only; no behavioral impact. Suggested fix: replace the `ComputeAllTargets()` clause with "after message drains (post-message-manager state)".

**M2 — Thin integration coverage for non-16-aligned cadence (nit).** The design's stated risk was a `frame`-vs-absolute-sample mix-up when block sizes aren't multiples of 16. `engine_audio_block_exposes_monotonic_start_sample` uses block size 10 and proves `startSample` advances absolutely (0 → 10), and the `ProcessSample` unit tests prove the interval logic — but the rig integration uses `preferredBlockSize = 32` (a multiple of 16), so no end-to-end test would catch an app that used `frame` instead of `startSample + frame` and still produced the correct cadence across a non-aligned boundary. The unit + engine coverage makes the residual risk low; worth a follow-up test only if you want belt-and-suspenders.

Neither finding blocks the change. M1 is a one-line comment fix I'd recommend before archiving; M2 is optional.
