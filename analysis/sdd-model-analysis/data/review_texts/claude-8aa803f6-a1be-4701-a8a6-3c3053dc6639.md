## Verdict: **FAIL**

One Task 2 contract is neither implemented nor tested, and it is exactly the one the prompt flagged: **descriptor-window behavior at the Braid4 LFO `maxLag = 256`.**

### Blocker — the pinned default descriptor window cannot serve `maxLag = 256`

The descriptor is implemented as a *total* `descriptorWindow`-element sequence with YIN differences computed **inside** that window, so the comparison count shrinks with lag (`DspAutoScope.hpp:1053` `comparisons = samples.size() - lag`). To keep at least one comparison at the largest lag (`maxLag + 1`), the constructor enforces:

```cpp
if (density.descriptorWindow <= config.maxLag + 1)   // DspAutoScope.hpp:1650
    throw std::invalid_argument("AutoScope density descriptor window is too short");
```

This ties the window size to `maxLag`: `descriptorWindow ≥ maxLag + 2`.

- **Default `maxLag = 64`:** `256 > 65` → fine. Comparisons stay ≥ 191. Works and is tested.
- **Braid4 LFO `maxLag = 256`:** `Braid4Core.hpp:329` sets `lfoScopeConfig.maxLag = 256` and inherits the **default** `density` (so `descriptorWindow = 256`). Validation evaluates `256 <= 257` → **true → constructor throws** `"descriptor window is too short"`. The LFO density AutoScope cannot be constructed at all. Even if the guard were bypassed, the difference loop divides by zero at `lag = 256` (`comparisons = 256-256 = 0`) and underflows `size_t` at `lag = 257`.

So the pinned default `descriptorWindow = 256` (which `sdsp-39` and the plan both fix) is fundamentally incompatible with the `maxLag = 256` path the density feature is meant to serve. The prompt's suspicion is correct: with a **total 256-element sequence** the model breaks at `maxLag = 256`; the descriptor must instead retain roughly `descriptorWindow + maxLag + 1` samples and keep a fixed `descriptorWindow` comparison count per lag (full-window YIN, `d(τ)=Σ_{i=0}^{W-1}(x[i]-x[i+τ])²`). That preserves the pinned "256-entry" descriptor while making it valid for any configured `maxLag`.

### Required fixes

1. **Remodel the descriptor window as full-window YIN.** In `ComputeDensityDescriptor`, read `descriptorWindow + maxLag + 1` retained samples (guarding retained-history availability accordingly) and, in `DescribeDensitySequence`, compute each lag's difference over a fixed `descriptorWindow` comparison count instead of `samples.size() - lag`. Keep the described sequence "256-entry" per `sdsp-39` line 95. Remove/relax the `descriptorWindow <= maxLag + 1` rejection (it exists only to paper over the shrinking-window bug) and size `densitySamples_` to the retained requirement, not to `descriptorWindow`.
   - *(Alternative only if the team deliberately rejects the pinned-256 model: have Braid4 override `density.descriptorWindow ≥ maxLag + 2` — but that contradicts the pinned default and the "256-entry sequence" wording, and it is not in this diff. The spec-faithful fix is the retained-samples model above.)*

2. **Add the missing `maxLag = 256` density test.** Every new density test uses default `maxLag = 64` or small configs; none exercises `maxLag = 256`. Add a case that constructs an AutoScope with `maxLag = 256` + default density, feeds enough LFO-rate history, and asserts a valid descriptor / non-empty reader (proving the pinned `descriptorWindow = 256` works there). This is the direct evidence line for the "Braid4 LFO maxLag=256" contract and would have caught the throw.
