## Review: Generic Encoder Position Feedback Plan

I cross-checked the plan (`docs/superpowers/plans/2026-07-16-add-generic-encoder-position-feedback.md`), the design doc, the OpenSpec `synchronize-absolute-encoder-feedback` artifacts (proposal/design/tasks/spec deltas), and the actual current `MidiController.hpp`/`.cpp`/`Engine.hpp` source.

**What checks out:**
- `EncoderMidiOutMapping{slotIx, position, cc}` has no channel field, matching the plan's need for a parallel `outputAddresses_` vector on `GenericMidiOutProcessor` rather than reusing the base mapping type.
- `ProcessPosition`'s current body hardcodes `kPrimaryPositionChannel = 0` at both its Twister and WrldBldr call sites (lines 1071, 1098) — the proposed signature change (adding `MidiControlAddress outputAddress`) and the "`{0, mapping.cc}`" call-site update for Twister/WrldBldr is a faithful, byte-for-byte-preserving refactor.
- `CreateMidiControllerProfile`'s current signature, the `if (config.encoderOutput.has_value()) { switch(...) }` block, and the pre-computed `activeAbsoluteFeedback`/`feedbackMode` locals are exactly where the plan's new `else if (profileKind == Generic && encoderInput.has_value())` branch would slot in, reusing those same locals as described.
- `Engine::RebuildMidiProcessors()`'s existing call site and its `controllers[ix]` snapshot make `controllers[ix].kind` trivially available for the new trailing argument — a source-compatible, additive change.
- Route-key shape `{controllerSlot, slotIx, position}` used by `EncoderMidiInProcessor::ReserveAbsoluteRoutes()` and `MidiOutProcessor::ReserveAbsoluteRoutes()` is identical, so a `GenericMidiOutProcessor` built from the same `encoderInput.turns` will reserve routes that line up with the paired input processor — the epoch-coordinator-reuse claim is structurally sound, not just asserted.
- `KindSupport(Generic)` already permits `encoderInput`+`encoderOutput` together, so the "explicit Twister/WRLD.Bldr output overrides" case is a legal, already-supported profile shape, not a new validity carve-out.
- `spm-78` and the `sar-7` scenario are genuinely new/unclaimed in `coverage.md`; the plan's one-line-per-requirement update format matches the existing convention (`spm-77` etc. have no dedicated `###` section either).
- Test infrastructure (`InstallInstrumentForTest`, `SingleControllerInstrument`, real `AbsoluteFeedbackCoordinator`) already supports everything Steps 1–3 ask for.

No Critical or Important findings — the design is internally consistent with the actual codebase and the single-task decomposition, while large, is justified by tight coupling (the new processor can't be tested without the address-parameterized `ProcessPosition`, which can't be tested without the factory wiring).

**Minor findings:**

1. **`GenericMidiOutProcessor`'s constructor (Step 6) doesn't show how `feedbackMode` reaches the base class.** `MidiOutProcessor`'s base constructor requires `EncoderMode feedbackMode`, but the plan's proposed derived constructor takes only `input` (no explicit mode param). The implementer must remember to thread `input.mode` through to the base ctor (via a helper that builds `EncoderMidiOutConfig` from `input.turns`). It's derivable and the design prose says "same feedbackMode ... as the input," but the C++ signature in Step 6 doesn't make this obvious.

2. **`ProcessPosition`'s `mapping` parameter becomes dead weight after the Step 5 refactor.** Today `mapping.cc` is `ProcessPosition`'s only use of `mapping`; once every enqueue branch switches to `outputAddress.channel/.cc`, `mapping` is passed in but unused inside the body (only `mappingIx` remains load-bearing, for `absoluteRoutes_[mappingIx]`). Harmless under `-Wall -Wextra` (no `-Werror` in this Makefile), but the plan doesn't flag it, and the signature could be simplified.

3. **`GenericMidiOutProcessor` inherits `MidiOutProcessor::SetConfig(EncoderMidiOutConfig)` unmodified.** Since `outputAddresses_` is a Generic-only side vector populated only at construction, a direct `SetConfig()` call (public, non-virtual, callable via a base or derived pointer) would desync `outputAddresses_` from `config_.mappings` and risk an out-of-bounds read in `Process()`. Not exercised today — Generic processors are always rebuilt fresh via `CreateMidiControllerProfile` — so this is latent, not live, but the plan doesn't mention hiding/guarding it.

4. **Wiring `controllers[ix].kind` into `RebuildMidiProcessors()` silently changes behavior for pre-existing Generic-kind `encoderInput`-only test fixtures beyond the "explicit specialized output" cases the plan calls out** — notably `TwoControllerInstrument()` in `rig_tests.cpp`, whose comment explicitly says "Both controllers' encoderOutput stays unset (deliberately)" to isolate an unrelated code path. I traced through its four consuming tests (`rig_two_controllers_output_feedback_isolated_per_sink`, `rig_reset_midi_output_processors_is_scoped_to_one_controller`, etc.): since `TwoControllerRigApp` has zero modulators and static default parameter values, the newly-attached `GenericMidiOutProcessor` would emit only during the priming round (which every affected test explicitly clears) and never resend afterward, so no assertion actually breaks. Step 8's mandated `rig_tests` run would catch it regardless if I'm wrong. Still, Step 9's verification language ("confirm all existing specialized-output tests still pass") undersells the real blast radius — it's worth the implementer explicitly re-reading `TwoControllerInstrument`-based tests rather than treating "specialized-output tests" as the only affected set.

PLAN VERDICT: PASS
