**Minor**

1. **Inconsistent header dependency for `DspMath.hpp` (build hygiene).** Native `projects/synth/Makefile:35` defines `RANDOM_LFO_HEADERS := DspRandomLfo.hpp GangedRandomLfoVisualizer.hpp` — omitting `DspMath.hpp` — whereas `projects/synth/browser/Makefile:12` includes it. Because the repo uses manual (not auto-generated) header prereq lists, an isolated edit to `ShapedInterpolate` in `DspMath.hpp` would not retrigger native rebuilds of `portable_ui_tests`, `browser_command_buffer_tests`, or `miniapp_system_tests` (only `dsp_tests` rebuilds, via `DSP_HEADERS`). Low impact and consistent with the pre-existing manual-dep pattern; a full `make test` is unaffected. Consider adding `DspMath.hpp` to the native `RANDOM_LFO_HEADERS`.

2. **Seqlock reader uses relaxed field loads (concurrency note, not a defect).** `detail::ReadGangedRandomLfoSnapshot` (`DspRandomLfo.hpp:208–237`) brackets relaxed per-field loads with two acquire loads of `revision`. Strictly, the second acquire load does not, in the C++ abstract machine, prevent the relaxed field loads from being reordered after it. This is harmless here: every published field is an individual `std::atomic` (so there is no data race / UB — only cross-field coherence is at stake), the odd/even + start==end revision guard rejects torn rounds, the writer's `release` store (`PublishUiState:372`) fences correctly, and this is the standard seqlock idiom. If strict-model cleanliness is desired, insert `std::atomic_thread_fence(std::memory_order_acquire)` before the second `revision.load`. Uncertainty: theoretical only; on the shipped x86/ARM targets and with all-atomic fields, behavior is well-defined and correct.

3. **Test-adequacy soft spots (all Minor; the underlying code is correct).**
   - *Process-before-`UpdateModValues` ordering* (`miniapp_system_tests.cpp:862–884`) is only conditionally discriminating: it asserts `modulators.Value(voice,3) == sources[voice]` at end-of-block, which distinguishes the two orderings only when the gang output differs between the block's final two samples (e.g. during a flat "waiting" phase it could pass under a reversed order). The code ordering itself (`MiniAppCore.hpp` per-sample loop: gang `Process` → copy outputs → `UpdateModValues`) is unambiguously correct; a single-frame block or a sentinel-leak assertion would harden the test.
   - *Solid-past / dashed-future segmentation* (`portable_ui_tests.cpp:257–298`): "solid past" is an existence OR (any polyline ending at/before present), not an assertion that the past is a single gap-free polyline; "alternating future" is existence-only (one gap), not a structural interleave/count check. Bounded-ness is separately pinned by the max-command-count assertion.
   - *Fail-closed* asserts command count `== 2` but not that the two are `Fill`+`Line`; the non-finite-bounds branch (which emits **zero** commands, `GangedRandomLfoVisualizer.hpp:57–62,157`) is untested.
   - `shaped_interpolate_preserves_double_progress` asserts `progress == originalProgress` after a by-value call — trivially true; the real no-writeback guarantee is covered by the voice test's exact double progress (`0.4`, `0.8`).

**Disclosed RED limitations (evidence notes, not present defects, per instructions):** the allocation-freedom test is structural/soak (10,000-call loop + `static_assert` on `std::array` storage) rather than a heap-instrumented guard; the Task-4 JUCE assertion RED could not be isolated.
