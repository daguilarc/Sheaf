# Review: Runtime-owned Emscripten AudioWorklet callback

I reviewed the AudioWorklet work across `BrowserRuntime.hpp`, `BrowserRuntimeAbi.cpp`, `worker.ts`, `audio.ts`, `main.ts`, the Makefile flags, and the C++/Playwright tests. The core design goal is met well: `ProcessAudioWorklet` drives the **same** `Runtime<App>`/`Engine<App>` instance via `runtime->Process` (BrowserRuntime.hpp:290-302) — no second app/runtime is constructed in the worklet, and there's no app-specific/concrete-app logic in the callback. The ABI additions and worker/protocol plumbing are generic. Findings below, most severe first, with uncertainty called out.

---

## 1. HIGH (uncertain) — Worklet-thread lifetime / use-after-free on shutdown
`BrowserRuntime.hpp:548-551` (`Destroy`) → `Stop` (`:56-70`) → `delete this`.

`Stop()` sets `started_ = false`, destroys the node/context, then `Destroy()` does `delete this`, which frees the `RuntimeAbiAdapter` — including the `Runtime` member and its `audioWorkletStack_` (BrowserRuntime.hpp:335), which is the very stack backing the running Wasm audio-worklet thread. There is **no join/stop of the worklet thread** — the code only calls `emscripten_destroy_web_audio_node` / `emscripten_destroy_audio_context`, and there's no `emscripten_stop_wasm_audio_worklet_thread`-style teardown.

Failure scenario: audio thread enters `ProcessAudioWorklet`, passes the `started_.load()` guard (BrowserRuntime.hpp:284); main thread concurrently runs `Destroy()`, frees the object + stack. The in-flight callback then dereferences a freed `runtime` and executes on freed stack memory → UAF / stack corruption on the realtime thread. Even the `started_` guard itself reads through the freed `runtime` pointer.

Uncertainty: this depends on whether `emscripten_destroy_audio_context` synchronously guarantees the render thread has quiesced before returning. I could not confirm that guarantee from the code; the standard Emscripten Wasm-audio-worklet model does not obviously join the audio thread synchronously. Worth confirming before relying on teardown during active playback (e.g. page-driven stop/reload while audio is running). If the guarantee doesn't hold, the fix is to ensure the worklet thread is stopped/quiesced before `delete this`.

## 2. MEDIUM — Callback logic has no portable (native/CI) test coverage
The entire callback body — channel-pointer striding, peak scan, `peak * 1'000'000` clamp (BrowserRuntime.hpp:304-306), synthetic timestamp accumulation, exception zero-fill — is inside `#ifdef __EMSCRIPTEN__` and is exercised **only** by the real-Chrome Playwright test (`audio-flow.spec.ts`, "real miniapp WASM runs DSP from the runtime-owned AudioWorklet callback"), which the design itself flags as environment-sensitive and requiring an unsandboxed Chromium. The native contract test (`browser_runtime_contract_tests.cpp:320-325`) only asserts `StartAudioWorklet()` returns `false`. So none of the arithmetic/channel logic is verified in a portable, sandbox-safe test — a regression there passes CI silently. Consider factoring the channel-mapping/peak math into a `#ifdef`-free helper that native unit tests can drive.

## 3. MEDIUM — Async start failures are swallowed; "started" doesn't mean "audio flowing"
`StartAudioWorklet` returns `true` immediately after kicking off `emscripten_start_wasm_audio_worklet_thread_async` (BrowserRuntime.hpp:114-121). The subsequent async callbacks each just `return` on failure with no state recorded: `AudioWorkletThreadInitialized` on `!success` (BrowserRuntime.hpp:219-221), `AudioWorkletProcessorCreated` on `!success` or bad channel count (`:236-242`), and node-creation failure (`audioNode_ == 0`, no branch). The JS side (`main.ts:44-48`) then resolves `{ started: true }` and the UI shows `audio:online`. If thread init, processor creation, or node creation fails, the user gets a silent, unrecoverable no-audio state with no diagnostic — the only signal is `AudioWorkletBlockCount()` staying 0. A channel-count mismatch at runtime has the same outcome: `Process` throws `invalid_argument`, gets caught, and zero-fills (BrowserRuntime.hpp:314-317) → silence with no surfaced error. Recording a failure/last-error status the UI can read would make these paths observable.

## 4. LOW–MEDIUM (uncertain) — Emscripten link/environment flags
`Makefile` sets `-sAUDIO_WORKLET=1 -sWASM_WORKERS=1` alongside existing `-pthread -sUSE_PTHREADS=1`, and changes `-sENVIRONMENT=worker` → `-sENVIRONMENT=web,worker`. Two things to confirm:
- AUDIO_WORKLET typically needs the `audioworklet` environment target included; explicitly restricting `ENVIRONMENT` to `web,worker` may omit it. If the unsandboxed real-Chrome test genuinely passes end-to-end (design claims it does), this is likely fine — but the explicit list is a landmine for anyone who adjusts it, and it's worth a comment noting why `audioworklet` is or isn't required.
- Mixing pthreads and Wasm Workers is supported but is a known sharp edge; worth a note that both are intentional (pthreads for the pool, WASM_WORKERS for the audio thread).

I flag this as uncertain because I can't run the Emscripten build here to confirm the worklet actually registers with this exact flag set.

## 5. LOW — `audioWorkletPeakMicrounits_` is an all-time max, never resets
The compare-exchange loop (BrowserRuntime.hpp:307-311) only ever raises the value; nothing decays or resets it. As a "did we produce non-silent audio" diagnostic (the test asserts `> 0`) it's fine, but as anything resembling a live peak meter it monotonically saturates and can't reflect later silence. Fine for current use; note it if the field is ever surfaced as a live meter.

## 6. LOW — Per-block full-buffer peak scan runs on the realtime thread in production
`ProcessAudioWorklet` scans every sample of every channel each callback (BrowserRuntime.hpp:298-303) purely for the diagnostic peak. That's O(channels × frames) extra work on the audio thread on every block, unconditionally (not gated to a debug/diagnostic mode). Small, but it's realtime-thread work added for instrumentation only.

## 7. LOW — Default runtime moved onto the main browser thread
`main.ts:170` now defaults to `createDirectRuntimeClient` instead of the worker client, so the whole runtime — per-frame `message-tick` + `build-ui-frame` (`main.ts:150`), `dispatch-action`, MIDI — runs on the main page thread. This is necessary for AudioContext creation (audio itself correctly runs on the dedicated worklet thread), but it regresses main-thread responsiveness versus the prior worker model. Not a correctness bug; a tradeoff worth acknowledging, especially since UI frame building is now synchronous on the main thread.

## Notes on the specific areas you asked about
- **Generic / no app-specific logic:** ✅ Callback and ABI are app-agnostic; nothing switches on a concrete app. Meets spec `sprs-8` scenario "No duplicated application runtime."
- **Same Runtime/Engine state:** ✅ `ProcessAudioWorklet` uses the shared `runtime->Process`; no duplicate runtime. This is the strongest part of the change.
- **Direct runtime request serialization:** ✅ The new promise-`queue` in `createDirectRuntimeClient` (`main.ts:33-38`) correctly serializes JS-driven control calls. Note it does **not** (and cannot) serialize against the audio-thread `Process` — that concurrency is by design and matches the desktop message-thread/audio-thread model. Since `Engine` already carries an `audioDeviceStateMutex_` (Engine.hpp) and desktop already calls `Process` off-thread, the browser is now exercising concurrency the engine was presumably already built for — but this is the first time the *browser* path hits true concurrent access (it previously serialized everything onto the worker), so any latent non-thread-safe read the desktop happens to avoid could newly surface. I couldn't fully audit `Engine::Process` vs. `Refresh`/`BuildUiFrame` reads here; flagging as something to keep in mind rather than a confirmed defect.
- **Channel-count handling:** Looks correct — `outputChannelCounts_[0] = channels`, `EXPLICIT` mode, guarded against `> kMaxBrowserOutputChannels` (32) in both node creation and the callback. The one soft spot is that a browser/engine channel mismatch degrades to silent zero-fill with no diagnostic (see finding 3).
- **AudioWorklet lifecycle/shutdown races:** Finding 1 is the main concern.
- **Fallback boundary:** ✅ Native path gated on `crossOriginIsolated`/`SharedArrayBuffer`; JS ring producer retained only when `worker.startAudioWorklet` is absent (`audio.ts:38`), matching the "diagnostic ring is fallback only" scenario. Idempotent re-start via `audioContext_ != 0` guard.
- **Test/spec coverage:** Spec updated coherently (`sprs-8`). Portable coverage gap is finding 2; the E2E DSP test correctly asserts `blocks >= 4 && peakMicrounits > 0`.

I did not modify any files.
