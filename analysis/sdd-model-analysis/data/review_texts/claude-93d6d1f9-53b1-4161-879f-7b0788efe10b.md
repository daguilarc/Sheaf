## Task 3 Review: JUCE Backend Interactive Draw Overlay

### Findings (by severity)

#### MEDIUM — Dead code in `IsRenderableKind` (`PortableJuceBackend.hpp`, diff line 268)

`Draw` was added to `IsRenderableKind`'s switch, but this case is unreachable. In `CollectRenderableDescendants`, Draw nodes are caught by the first `if (node->kind == NodeKind::Draw)` branch, so the `else if (IsRenderableKind(...))` branch never fires for them. The draw-node routing into `m_renderedNodeIds` happens correctly through `IsInteractiveDrawNode` inside the first branch — the `IsRenderableKind` case does nothing. The brief explicitly sanctions this ("this is acceptable because only interactive draw IDs are added to `m_renderedNodeIds`"), so it's not a spec violation, but the added case gives a false impression of the control flow to future readers.

#### MEDIUM — Silent delta-drop when action value lacks a colon (`PortableJuceBackend.hpp`, diff lines 203–210)

In `DispatchCurrentNodePointerDragAction`, when `dispatched.value` is non-empty but contains no colon, the `rfind` returns `npos`, the `if` body is skipped, and the original action is dispatched unchanged — the computed `delta` is silently discarded. The spec doesn't spell out this edge case, but dispatching an action with a stale value is worse than not dispatching at all. In the current miniapp encoder wiring, the value always contains a colon, so the test passes; but the silent drop is a latent correctness hazard for any future action string that omits one.

#### LOW — JUCE production hit-testing unverified by test (`MiniAppJuceBackendParityTests.cpp`, diff lines 47, 52, 63)

The test calls `encoder->mouseDown(...)`, `encoder->mouseDrag(...)`, and `encoder->mouseDoubleClick(...)` directly on the returned component pointer, bypassing JUCE's component-tree hit-testing entirely. This confirms dispatch wiring but does not confirm that the overlay has correct bounds set in production so JUCE would route real pointer events to it. The existing layout machinery likely handles this because interactive draw nodes are now in `m_renderedNodeIds`, but it is not proven by the test coverage added here.

#### LOW — `setPaintingIsUnclipped(true)` on an empty-paint overlay (`PortableJuceBackend.hpp`, diff line 129)

`InteractiveDrawComponent::paint` is a no-op. `setPaintingIsUnclipped(true)` is a painting performance hint that has no effect when the component never paints. Harmless, but noise.

#### LOW — `std::to_string(float)` is locale-sensitive (`PortableJuceBackend.hpp`, diff line 208)

`std::to_string(delta)` is affected by the active locale's decimal separator. On systems where `,` is the decimal character, the embedded value string becomes `"0,050000"` and downstream parsing would fail silently. Consistent with some existing patterns, and unlikely to hit in practice with the current locale assumptions, but worth noting.
