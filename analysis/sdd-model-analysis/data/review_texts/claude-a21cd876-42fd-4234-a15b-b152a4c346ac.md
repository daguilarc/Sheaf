Offsets are pinned by exact-byte assertions on both sides (record+21/25/29/33). Legacy records (kinds 0–10) are byte-unchanged.
- **Validation-before-allocation ordering.** Both decoders finite-check bounds, reject zero dims, enforce the 4096/1,048,576 caps, and require `byteCount == cells` **before** `Section(byteCount)`/`byteArray(byteCount)` (`BrowserCommandBuffer.hpp:589-591`, `protocol.ts:222-227`). A forged 4-billion `byteCount` is rejected at `byteCount !== cells` since `cells ≤ 16M`, so no oversized allocation is reachable. Division `max()/height` is guarded by the prior `height==0` throw.
- **Truncation/excess.** Section-bounded readers plus the `!reader.Empty()` / `!drawsReader.empty()` trailing checks catch both, and the tests mutate real serialized bytes through the production decoder to prove it.
- **Immutability / forged-kind safety.** Payload dims+bytes live in a private `AlphaRasterPayload` reachable only via the friend factory; `ValidatedRaster()` (`PortableUI.hpp:154-159`) re-runs full validation, so a forged `kind = AlphaRaster` on a default/Fill command throws (empty payload), and post-construction `bounds` mutation to non-finite throws. ### Non-blocking findings (recommend, do not block)

1. **Dead/unreachable overflow guards → misleading test coverage.** `PortableUI.hpp:60-62` (`width > size_t_max/height`) and `protocol.ts:158` (`!Number.isSafeInteger(cells)`) are unreachable: width/height are already capped at 4096, so `cells ≤ 16,777,216` can never overflow `size_t` or exceed `Number.MAX_SAFE_INTEGER`. Consequently the C++ test at `browser_command_buffer_tests.cpp:240-242` labeled "multiplication overflow rejected before allocation" actually trips the *dimension-exceeds-limit* branch (UINT32_MAX > 4096), not the overflow branch — the overflow line has zero coverage. Either drop the guards as redundant or relabel the test; as-is the report's "checked-product" claim overstates what's exercised.

2. **Unconditional version bump.** The encoder emits v2 for *every* frame, including the common no-raster case (`BrowserCommandBuffer.hpp:500`), so any independently-deployed older decoder would reject 100% of frames, and the v1 read-path now has no producer. Safe under the atomic C++/WASM+TS co-deploy this repo uses, and the legacy read support is harmless defense-in-depth — flagging only so the "legacy compatibility" framing isn't mistaken for cross-version interop.

3. **No cross-language golden test.** Each side round-trips against its own encoder/fixture; nothing asserts C++-encoded bytes decode in TS (or vice-versa). Wire agreement rests on the exact-offset assertions matching on both sides. This mirrors the pre-existing pattern for other draw kinds, so not introduced here, but a single shared byte-vector fixture would harden the parity guarantee.

None of these affect correctness or safety of the shipped path, so the change is approvable as-is.
