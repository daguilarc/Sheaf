1. **blocker** — `specs/synth-app-runtime/spec.md:82-99`, `design.md:225-258`, `tasks.md:22`, `projects/synth/src/PatchPersistence.cpp:336-371`, `projects/synth/include/synth/Json.hpp:250-273,679-691`
   Problem: the audio callback is required to drain `patchInputBus` via `ApplyPatchMessage`, but save serialization allocates (`make_shared<JsonArena>`, `GrowAndReset`, `Dumps` malloc), and patch message movement/destruction carries `std::string`/`shared_ptr` work. This contradicts the real-time-safety claim.
   Suggested fix: do not consume the current patch command bus on the audio thread. Split patch operations into RT-safe apply messages only, move save serialization/file-adjacent work to message/IO thread, or introduce a preallocated RT command format with explicit tests proving no allocation/locks in the callback.

2. **major** — `specs/synth-app-runtime/spec.md:98-112`, `design.md:225-227`, `projects/synth/src/ParameterModulation.cpp:2707-2719`
   Problem: sar-7 promises UI and MIDI messages use shared timestamps and are applied in timestamp order, but D5 processes all visible UI-bus messages, then all MIDI-bus messages. Two SPSC queues cannot provide cross-bus timestamp ordering unless the engine merges queue heads.
   Suggested fix: either weaken the requirement to per-bus FIFO visibility, or specify and implement a merged drain that peeks both queues and applies the earliest visible timestamp first.

3. **major** — `specs/synth-app-runtime/spec.md:82-92`, `design.md:228-235`, `projects/synth/src/ParameterModulation.cpp:2098-2105`, `projects/synth/miniapp/Main.cpp:669-705`
   Problem: the proposed pump calls `ParameterManager::ComputeAllParameters()`, but that method calls `SnapCurrentToTarget()`, bypassing the `ProcessLite` slew that the miniapp currently preserves by calling per-parameter `Compute()` before its DSP loop.
   Suggested fix: add/use a manager-level “compute targets only” API for the audio pump, or explicitly make the app responsible for target computation before `ProcessLite`. Add a behavior parity test for smoothing.

4. **major** — `specs/synth-app-runtime/spec.md:33-42,150-151`, `design.md:249-254`
   Problem: sar-3 says apps may dereference all `AppContext` members from any hook, but the context exposes RT-unsafe/message-thread-only objects (`PatchManager`, `MidiSender`, patch buses, parameter storage replies). This also conflicts with sar-10’s “UI renders without touching the parameter manager directly.”
   Suggested fix: make the context contract thread-specific: audio hook gets only audio-safe manager/app state, UI gets producer-only buses/UI state, patch/MIDI commands go through runtime methods or narrow façade types.

5. **major** — `specs/synth-async-logging/spec.md:18-31`
   Problem: the logger says “any project thread” logs to “that thread’s own queue,” but queues are per `ThreadId`, not per physical thread. Multiple untagged threads all share `Unknown`, and any future duplicate role threads would violate the SPSC premise.
   Suggested fix: either make queues truly per physical thread, make shared role queues MPSC, or require unique tagging for every producer and disallow concurrent `Unknown` producers. Add concurrent producer tests.

6. **major** — `specs/synth-app-runtime/spec.md:22-31,64-65,173-174`, `tasks.md:21,41`
   Problem: `Engine::Initialize()` is tasked with calling the app prepare hook using “negotiated/configured values,” but sar-12 says engine init excludes device steps and task 6.1 negotiates the audio device later in `Runtime`. The engine cannot know negotiated sample rate/block size during initialization.
   Suggested fix: move `PrepareToPlay` out of `Engine::Initialize`; have `Runtime` call it after device open/device change, and have `SynthRig` call it explicitly with config/test values.

7. **major** — `specs/synth-app-runtime/spec.md:64-65,114-128`, `tasks.md:21,41,45`
   Problem: startup ordering builds MIDI processors before startup patch application, then reopens persisted endpoints after `Initialize()`. If the startup patch changes the profile, tasks do not explicitly require a rebuild before endpoint reopen.
   Suggested fix: specify that startup patch load triggers the same rebuild/reopen notification path as runtime load, and add an ordering test: patched profile is installed before persisted devices are reopened.

8. **minor** — `specs/synth-app-runtime/spec.md:114-119`, `design.md:464-466`, `projects/synth/miniapp/Main.cpp:464-496`, `openspec/specs/synth-patch-persistence/spec.md:49-51`
   Problem: startup patch selection says “most recently modified patch directory,” while the existing miniapp fallback selects by latest sortable version filename, then patch directory name. The design also claims mtime matches the existing scan, which it does not.
   Suggested fix: choose one deterministic rule. Prefer the existing sortable-version rule unless there is a migration reason, and add scenarios for ties and multiple patch directories.

9. **minor** — `specs/synth-async-logging/spec.md:69-74`, `tasks.md:22`
   Problem: slog-6 calls log stamps “sample-accurate,” but the runtime-owned counter is advanced per block while `ProcessBlock` owns the per-sample loop. Logs inside a block can only be block-position stamps unless the app updates the counter per sample.
   Suggested fix: rename this to block-accurate audio position, or define an app-visible/sample-loop mechanism for true per-sample stamping.

10. **minor** — `specs/synth-app-runtime/spec.md:184-205`, `tasks.md:28-31,54`
   Problem: `SynthRig` patch helpers “pump until response” with no timeout, maximum block count, or failure result. A dropped/full queue or invalid patch can hang tests.
   Suggested fix: require bounded pumping with a status/error return and add tests for queue-full/invalid-patch timeout paths.
