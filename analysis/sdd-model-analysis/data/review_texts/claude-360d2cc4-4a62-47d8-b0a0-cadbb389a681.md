## Findings

### 1. Realtime AudioWorklet path no longer allocates for DOM UI actions — ✅ fixed
- The realtime callback `ProcessBrowserAudio` → `sheaf_browser_process` (`BrowserMiniAppHost.cpp:328-345`) now does only `DrainMidiInput` + `engine->ProcessBlock`. The prior `state.status = …Ready` write was removed (`BrowserMiniAppHost.cpp:342`), and it never calls `RefreshUiFrame`.
- All UI-frame serialization (`RefreshUiFrame`, which allocates a `SerializedFrame` tree + `std::string` JSON at `BrowserMiniAppHost.cpp:129-140`) now runs only on main-thread-invoked exports: `sheaf_browser_create`, `sheaf_browser_message_tick`, and `sheaf_browser_dispatch_action` (`:305`, `:369`, `:383`). `dispatchAction` is driven from the main JS thread (`runtime.js:104-107`), not the worklet.
- `DrainMidiInput` reuses `midiScratch.raw`, which is `reserve()`-d to capacity in the `HostState` constructor (`BrowserMiniAppHost.cpp:52-53`), so `clear()`+`insert()` up to `kMaxBrowserMidiMessageBytes` won't reallocate.
- Minor note (not the asked question): on Emscripten, `MidiSender::Enqueue` takes `std::lock_guard(mutex_)` synchronously on the audio thread (`MidiController.cpp:595-608`). It only pushes to a lock-free SPSC queue in `Send`, so no allocation — but it is a lock taken on the realtime thread.

### 2. Chrome storage smoke now covers IDBFS reload persistence — ✅ covered
- New `tests/smoke/storage-smoke.mjs:42-93` launches real Chrome (playwright), writes config/patch/log files via `FS`, calls `FS.syncfs(false)` to persist to IDBFS (`:70-72`), does a full `page.reload()` (`:75`), re-waits for the prepared synth (which re-mounts and `syncfs(true)` loads from IDBFS via `prepareBrowserSynth`), then reads the three files back and asserts their contents (`:77-88`). A full page reload discards the wasm heap, so surviving values genuinely prove IDBFS (IndexedDB) persistence, not MEMFS.
- Wired into `make smoke` (`Makefile:32-33`), so it actually runs.

### 3. MIDI output routing to a selected browser output port — ⚠️ present at API level only, not UI-wired
- The adapter supports it: `selectedOutputPortId` ctor field + `setSelectedOutputPortId` (`midi.js:186-231`), and `drainOutput` resolves `selectedOutputPortId ?? defaultOutputPortId()` (`midi.js:234`). Unit-tested with a two-port select + re-select (`midi.test.mjs:141-168`).
- **Gap:** nothing in `boot.js`/`ui-renderer.js` ever calls `setSelectedOutputPortId` or passes `selectedOutputPortId`. `initializeBrowserMidi` constructs the adapter without it (`boot.js:36-40`), and the render-loop `drainOutput` uses the default resolver (`boot.js:56-58`). So `selectedOutputPortId` stays `null` and output always falls back to the first port (`defaultOutputPortId`, `midi.js:253-255`). A caller can select a port only programmatically via `globalThis.sheafMidi.setSelectedOutputPortId(...)`; there is no user-facing port picker.

**Verdict:** Items 1 and 2 are solidly addressed. Item 3's routing mechanism exists and is tested but isn't surfaced through any UI/boot wiring — if the requirement is that a *user* can target a selected output port, that end-to-end path is still missing.
