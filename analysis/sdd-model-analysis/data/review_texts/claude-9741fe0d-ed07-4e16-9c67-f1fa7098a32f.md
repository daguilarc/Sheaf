### Issues

#### Critical (Must Fix)
None. Judged as a scaffold slice, nothing blocks merge.

#### Important (Should Fix)
- **`DrainMidiInput` allocates on the audio callback path** — `BrowserMiniAppHost.cpp:28-47`, called from `sheath_browser_process` (`:88`). Each queued message does `std::vector<std::uint8_t> bytes; bytes.reserve(...); push_back(...)`, directly violating the plan's "no unbounded allocation on the realtime path" constraint. It is honestly disclosed in task-8 ("Realtime MIDI drain currently allocates"), so it's an accepted deferral — but it sits in the literal realtime entry point and sets a bad pattern for the next phase. Fix direction: drain into a preallocated fixed buffer / pass `MidiMessage.bytes` span into the processor without heap allocation before wiring the real audio path.
- **`sheath_browser_ui_frame()` bumps `frameVersion` and hard-codes `dirty=1` on every call** — `BrowserMiniAppHost.cpp:155-170`. Because version changes on *read*, both `BrowserRuntime.readFrame`'s `version === lastFrameVersion` skip (`runtime.js:73`) and the renderer's identical guard (`ui-renderer.js:131`) can never short-circuit; once the real render loop is wired this forces a full `root.replaceChildren(...)` DOM rebuild every animation frame. Disclosed as the "producer always-dirty" scaffold, but the version-increment-on-read coupling specifically makes the dirty/version plumbing untestable until fixed — flag it prominently so the next phase doesn't mistake the plumbing for working. Fix direction: derive `dirty`/`version` from actual tree change, and don't mutate version inside the const-ish getter.

#### Minor (Nice to Have)
- **`BigInt` tick vs. wasm build flags** — `runtime.js:50` calls `sheath_browser_message_tick(BigInt(...))` for the `uint64_t` param, but the `wasm` Makefile target (`Makefile:34`) omits `-sWASM_BIGINT`. Against a real build the u64 lowers to two i32s and the BigInt call throws. Latent (exports path is deferred); note it for the Emscripten build task.
- **Partially-initialized global on failure** — `boot.js:155` sets `globalThis.sheathRuntime = runtime` *before* the storage gate `requireBrowserStorageModule` throws at `:158`. The already-running render loop then polls a runtime whose engine was never created. Harmless with the current stub (missing `ui_dirty`/`ui_frame` exports → `readFrame` returns null), but worth setting `sheathRuntime` only after the gate passes.
- **MIDI permission prompt at page load** — `boot.js:242-244` calls `initializeBrowserMidi()` at module import time whenever `requestMIDIAccess` exists. With `{ sysex: true }` Chrome surfaces a permission prompt on load rather than from user activation; the plan suggested "after page load or an explicit MIDI enable action." Minor UX/consent nit.
- **5.2 checkbox is mildly generous** — `midi.js:mapMidiPorts` maps ports to plain JS shapes (`id/identifier/name/manufacturer/type/state`), not into the synth's actual device-list/endpoint-reference types (that integration is 5.5, correctly unchecked). Defensible as a "surface," but the mapping isn't verified against the synth concept it claims.
- **MIDI routing claim not test-covered** — `BrowserMidiAbiTests.cpp` only asserts enqueue/reject and an empty output drain; it never drains into a `MidiInProcessor`. The task-5 report's "queued input bytes drain ... forwarded into each existing MidiInputProcessor" is compile-verified only, not behavior-verified. Consider a native test that creates the host, enqueues, processes a block, and asserts the processor observed the message.

### Recommendations
1. Before the realtime audio path is wired (next phase), fix the two Important items together: preallocate the MIDI drain and make `dirty`/`version` reflect real change rather than read-count. These are the two things most likely to mislead the next implementer into thinking the plumbing works.
2. Add one native behavioral test that drives `enqueue → process block → processor observed input` so the "routes into MIDI bus" claim is verified, not just linked.
3. When the Emscripten build task lands, decide `-sWASM_BIGINT` vs. two-i32 tick and align `runtime.js` accordingly.
4. Move the module-load MIDI request behind a user gesture / explicit enable, and defer setting `globalThis.sheathRuntime` until after the storage gate.
