### Important

**1. `LaunchMiniApp` can throw out of a JUCE button callback with no handler → `std::terminate`**
`apps/sheaf-synth/Main.cpp:73-81`

```cpp
void LaunchMiniApp(synth::RuntimeDataPaths paths) {
    auto session = std::make_unique<RuntimeShellSession<MiniApp>>(std::move(paths));
    ...
}
```

`RuntimeShellSession`'s constructor calls `runtime_->Start()`, which can throw (device init, `create_directories`, engine init). This runs from a `juce::TextButton::onClick` → `ActivateApp` → `registration.launch(...)` chain. JUCE does **not** wrap widget callbacks in try/catch — the same reasoning `ShellApplication::initialise` documents at `Shell.hpp:122-147` ("JUCE does not wrap initialise() in a try/catch…") applies verbatim to button callbacks. An exception here unwinds straight through the framework and aborts the process. `initialise()` is guarded; this launch path is not. Recommend a try/catch in `LaunchMiniApp` mirroring `initialise()`'s (log, stay on the launcher rather than tearing it down).

**2. Launcher destroys itself (and the live button/closure) synchronously from within its own click**
`apps/sheaf-synth/Main.cpp:79`, reached via `Launcher.hpp:45-47,119-129`

`LaunchMiniApp` calls `launcher_.reset()` while the stack is *inside* that launcher's `TextButton::onClick` → `LauncherComponent::ActivateApp` → the `registration.launch` `std::function`. `reset()` destroys the `LauncherComponent`, its `rowButtons_` (the executing button, whose `onClick` `std::function` is mid-invocation), and `apps_` (the `launch` `std::function` also mid-invocation). This likely survives because JUCE guards event dispatch with `BailOutChecker` and `ShowContent` detaches the launcher from the window before the reset — but destroying a component and the very closures on the call stack is a fragile pattern to rely on. Deferring teardown via `juce::MessageManager::callAsync([this]{ launcher_.reset(); })` (or resetting the launcher after control returns to the message loop) removes the hazard cheaply. Worth confirming rather than leaving implicit.

**3. `sheaf-synth` build under-specifies header dependencies → stale binary on MiniApp header edits**
`apps/sheaf-synth/Makefile:10,18`

```make
APP_HEADERS := $(APP_DIR)/Launcher.hpp $(APP_DIR)/../miniapp/MiniAppRegistration.hpp
```

`Main.cpp` includes `MiniAppRegistration.hpp` → `MiniApp.hpp` → `MiniAppCore.hpp`, `MiniAppUI.hpp` (→ `MiniAppUiModel.hpp`, `MiniAppDraw.hpp`, `DemoModulation.hpp`). None of those are listed here, and `juce_build.mk`'s `SYNTH_JUCE_HEADERS` glob covers only `juce/*.hpp` + named `runtime/` headers — **not** the `apps/miniapp/` app headers (confirmed at `juce_build.mk:50`). So editing `MiniApp.hpp`/`MiniAppCore.hpp`/`MiniAppUI.hpp`/`MiniAppUiModel.hpp`/`MiniAppDraw.hpp`/`DemoModulation.hpp` rebuilds neither `SheafSynth` nor the launcher-harness test (`$(LAUNCHER_HARNESS_TEST)` also depends on `$(APP_HEADERS)`). `apps/miniapp/Makefile:28` lists all of these explicitly for exactly this reason; the sheaf-synth Makefile should mirror that list.

### Advisory

**4. CWD-relative data root is non-writable when launched as a bundled `.app`**
`apps/sheaf-synth/Main.cpp:25-26` — `getCurrentWorkingDirectory().getChildFile("data")`. Launched from Finder, CWD is typically `/`, so this resolves to `/data` and `create_directories` fails (silently logged in `Runtime::Start`). Fine for dev/repo-relative use per the spec, but flag for the eventual shipped bundle — it diverges from `Runtime::DefaultDataPathsForApp`'s `userApplicationDataDirectory` resolution.

**5. `check_ui_boundary.sh` doesn't exclude `apps/sheaf-synth/build/**`**
`scripts/check_ui_boundary.sh:16` excludes `build/**` and `apps/miniapp/build/**` but not the new `apps/sheaf-synth/build/`. Harmless today (build dir holds only `.o`/binary/plist, no scanned source extensions), but asymmetric with the miniapp exclusion and a latent footgun if a generated source ever lands there.

**6. Inconsistent invalid-appId exception messages**
`AppRegistry.hpp:73` throws `"invalid synth appId"` (no id) while `AppRegistry.hpp:59` throws `"invalid synth appId '<id>'"`. The contract test at `contract_tests.cpp` only asserts `find("appId")` for the registration path but `find("../escape")`/`find("''")` for the paths path, so both pass — but the divergence is a minor maintenance wart; unifying the messages would let the tests assert identically.

**7. `Info.plist` has no `NSMicrophoneUsageDescription`**
Correct for the miniapp (`RuntimeConfig::numAudioInputs` defaults to 0, so no input device is opened and macOS won't prompt). Note for any future registered app that requests inputs — without the key, macOS 10.14+ hard-crashes on input-device open.

**8. Minor test brittleness (acceptable)**
`engine_tests.cpp` `sheaf_synth_runtime_configuration_...` asserts `contents.find("0.55") == npos` — a coincidental-substring guard riding alongside the real `find("parameters") == npos` check; and `LauncherHarnessTests.cpp:52-54` pins the exact row-format string. Both are legitimate contract assertions; noting only that they'll need updating in lockstep with format changes.
