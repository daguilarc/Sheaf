**I2 — Outbound MIDI (incl. SysEx) is drained only on the ~500 ms poll timer.** `projects/synth/browser/src/midi.ts:91` `drainOutputs()` is called from exactly one site — the tail of `reconcile()` at `midi.ts:125` — and `reconcile()` runs only via `poll()`, which fires on `onstatechange` and the periodic interval (`midi.ts:74`, default `pollIntervalMs ?? 500`). There is no frame-loop or dedicated fast drain (`main.ts` never calls into MIDI draining). So app→device messages sit queued up to ~500 ms and only flush when a device-enumeration poll happens. Bidirectional MIDI is functionally present and tested (`midi-flow.spec.ts:335-336` asserts outbound SysEx `F0…F7` flows), so the spec's "bidirectional MIDI" requirement is *met* — but the outbound path's latency is coupled to the device-enumeration cadence, which is poor for real-time MIDI-out (CC feedback, SysEx dumps). Secondary: `drainOutputs` caps at 256/pass (`midi.ts:94`) and the C++ `OutputSink` caps at 256 (`BrowserMidiBridge.hpp:206-209`) with no overflow signal, so a burst exceeding 256 between polls is silently dropped.

*Uncertainty / scope:* This drain architecture predates this change (it's from the browser-wasm-runtime layer), and the requirement under review specifies bidirectionality, not latency. I flag it as important because it's a genuine functional-quality defect in a shipped feature, but it's arguably out of this change's core scope — your call whether to fix now or file a follow-up.
