**Blocker 2 — audio channel count assumed stereo, could corrupt memory → RESOLVED.**
The count is now queried from the runtime rather than assumed, and it flows consistently end-to-end:
- C++ ABI adds `synth_browser_audio_output_channels` → `Runtime::AudioOutputChannels()` returning `engine_.Config().numAudioOutputs` (`BrowserRuntime.hpp:53`).
- `main.ts:167-171` requests `audio-config` and passes `channels` into `AudioBridge`, which propagates it into the ring `descriptor.channels`.
- `worker.ts:272` renders with `bridge.descriptor().channels`, and `worker.ts:118-123`/`emscriptenRuntimeFacade` allocates exactly `channels` buffers and passes `outputChannels` into `_synth_browser_process`.
- `Runtime::Process` (`BrowserRuntime.hpp:64-75`) now **validates** `outputChannels == engine_.Config().numAudioOutputs` and throws on mismatch, and sets `block.numOutputChannels` from the caller-supplied (validated) count instead of blindly writing `numAudioOutputs` channels into a JS-allocated buffer.

I confirmed the timing is safe: `config_ = App::Config()` is assigned in `Engine::Initialize()` (`Engine.hpp:120`), which runs via `Runtime::Start()` during the ABI `initialize` step — i.e. **before** `audio-config` is queried and before `Prepare`. So `numAudioOutputs` is populated when read. The JS allocation size and the engine's write count are now provably equal, and any divergence fails closed with `std::invalid_argument` (caught by `Invoke`, surfaced as status `-1`) — no out-of-bounds write. Memory-corruption path is closed.
