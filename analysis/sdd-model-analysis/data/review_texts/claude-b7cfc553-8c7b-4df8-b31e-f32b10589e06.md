1. **`projects/synth/runtime/JuceRuntimeMainServices.hpp:72-100`** — Gating output/input device-name enumeration behind `audioSyncPending_` (now defaulting to `true` at line 221, set only via `SetAudioSyncHook` at line 27) changes observable behavior versus the immediately-prior commit: `RefreshAudio()` used to re-enumerate `getDeviceNames()` unconditionally on every ~33 ms UI tick, so a hot-plugged/removed audio interface would appear/disappear from the Audio page's combo boxes within one frame. After this fix, the name list only refreshes when `audioSyncHook_` fires (i.e. on an engine-driven audio-device-changed event — patch load/revert, runtime-config load, or an explicit device switch). No `juce::AudioDeviceManager::ChangeListener` is wired anywhere in `Runtime.hpp`, so a raw OS hot-plug event with no accompanying engine-level change won't refresh the combo's device list until some other sync event happens to fire. This is very likely the *intended* design given the hook's naming/doc comments (the old unconditional enumeration was itself the "dead flag" bug the prior review flagged, not a deliberate feature), so I'm not raising it as a regression — but it's a real, untested behavior change worth confirming is accepted, since it wasn't called out in the commit message.

JUCE's own event dispatch is built to tolerate a component destroying itself from within its own click callback (`Component::BailOutChecker` guards `internalMouseUp`/`internalClickCallback`), so I don't believe this is a live bug, but there's no test that drives a real synthesized mouse event through JUCE's dispatch machinery to confirm it end-to-end — worth a note if this pattern is ever extended to a widget that isn't going through JUCE's guarded dispatch path.
