## Code Review — `add-browser-wasm-runtime`

### Summary
The generic runtime is genuinely well-built. `Runtime<App>` sits over `synth::Engine<App>` with no app knowledge; the MIDI bridge reuses `PlanMidiReconciliation`/`ExecuteReconcilePlan` rather than reimplementing policy in JS (design D5 honored); the command buffer is a clean JUCE-free serializer with defensive bounds-checked decoders on both the C++ and TS sides; audio uses a Worker-owned WASM + AudioWorklet + SAB ring bridge with a cross-origin-isolation gate; persistence is app-scoped IDBFS with root-constrained patch paths; the static server sets COOP/COEP + `midi=(self)` and rejects traversal. The `check-generic-runtime.mjs` gate and `not.toMatch(/MiniApp|synth_miniapp/)` assertions enforce the no-concrete-app-logic boundary, and `miniapp_entry.cpp` / `fake_app_entry.cpp` name only the app type via `SYNTH_BROWSER_APP`. Verification evidence (C++ tests, 20 pass + 1 expected real-WASM skip, strict openspec validate, `git diff --check`) is consistent with what I read.

Findings ordered by severity.

---

### 1. (Important) No product boot: `main.ts` is a stub, so the shipped static site does not open the app
`projects/synth/browser/src/main.ts:1-11` only *defines and exports* `installBrowserAudioActivation`; nothing calls it at module load. `public/index.html:5` loads `../dist/src/main.js`, so serving the build and opening the page instantiates an empty `#synth-root` — no worker created, no WASM loaded, no UI rendered, no MIDI/audio wired.

Every "app open / audio / MIDI / gestures" assertion is satisfied by the Playwright harness assembling the runtime graph itself inside `page.evaluate` (`fake-app.e2e.spec.ts:34-183` imports the real `/dist/src/*.js` modules and hand-wires `BrowserRuntimeWorker` + `AudioBridge` + `BrowserMidiManager` + `BrowserUiBackend` + `BrowserPersistence`). The ~40 lines of composition-root glue that would live in `main.ts` (load → create → initialize → build-ui-frame → render loop → connect UI actions/audio/MIDI to the worker) exist only in tests.

This diverges from the plan's own File Structure ("`main.ts`: main-thread bootstrap … worker/audio/MIDI/UI/persistence orchestration") and from spec `sbw-2` ("the app opens, initializes its browser runtime, loads its WASM module, installs its worker and AudioWorklet, and can run") and `sbw-9` ("app open"). The individual runtime pieces are functional and tested; what is missing is the top-level wiring that makes the deliverable static website actually run. Tasks 8.3/8.4 are checked complete, so this gap is not currently disclosed anywhere. Recommend: implement the `main.ts` composition root (or, if intentionally deferred, uncheck the affected tasks and note it explicitly).

### 2. (Medium) Audio output channel count is hardcoded to 2, not negotiated from `Config().numAudioOutputs`
`AudioBridge` defaults `channels = 2` (`audio.ts:29`), the ring is created with that count, and `worker.ts:265` calls `renderAudio(handle, bridge.descriptor().channels, frames, …)` allocating exactly `channels` output pointers. But C++ writes `block.numOutputChannels = engine_.Config().numAudioOutputs` (`BrowserRuntime.hpp:69`), default 2 (`AppContext.hpp:27`) but app-configurable. For a conforming app with `numAudioOutputs > 2`, `ProcessBlock` writes `outputs[2]`, `outputs[3]`, … beyond the 2-entry pointer table → out-of-bounds read of the WASM heap as a channel pointer → writes samples to an arbitrary heap address (memory corruption). For `numAudioOutputs == 1`, channel 1 of the ring reads uninitialized `_malloc` memory. Nothing asserts `descriptor().channels == numOutputChannels`. This contradicts the "compile-time swappable over any conforming `SynthApplication`" requirement — audio is correct only for 2-channel apps. Recommend deriving ring channel count from the engine config (or asserting equality and failing clearly).

### 3. (Low) Ring-buffer overflow silently drops rendered frames with no accounting
`SharedRingBuffer.write` (`protocol.ts:52-67`) clamps `count` to free space and discards any excess frames the worker already rendered; only underflow is counted (worklet `underflowCount`), there is no overflow counter. Because C++ advances the engine sample position by the full `block.numFrames` regardless, dropped output frames become an inaudible-position-preserving glitch under render-ahead bursts, with no diagnostic. Acknowledged as a first-pass trade-off in the design's risk list, but worth an overflow counter symmetric to underflow for observability.

### 4. (Low / latent) `process` ABI path passes null output pointers
The `process` worker command → `emscriptenRuntimeFacade.process` calls `_synth_browser_process(handle, 0, frames, …)` (`worker.ts:111`); C++ then sets `block.outputs = nullptr` and calls `ProcessBlock`. The fake app null-guards (`FakeBrowserApp.hpp:67`), but a conforming app that assumes non-null outputs would fault. Real audio always uses `render-audio`/`renderAudio` with real buffers, so this path is test-only today, but it's exposed in the protocol. Low.

### 5. (Nit) MIDI output slots beyond `MidiSender::kMaxSinks` can't bind an output
`ResizeForControllers` (`BrowserMidiBridge.hpp:252-261`) only creates `OutputSink`s up to `kMaxSinks`; higher slots get a null sink, so `openOutput` returns false and the reconcile plan likely re-attempts each poll. Input still works. Edge case (many controllers); the comment documents the limitation. Acceptable.

### Open questions / assumptions
- I assumed `Engine<App>` exposes `InstrumentSnapshot`, `EditInstrument`, `MidiInputProcessor`, `ResetMidiOutputProcessors`, `Context().midiSender`, and `MidiSender::kMaxSinks` as used by the bridge; since `make -C projects/synth test` and the bridge test compiled, these are real.
- I did not execute anything (reviewer role = read-only); I relied on the controller's stated verification results.
- The real-WASM smoke skip is legitimately conditional on the `dist/wasm/miniapp.js` artifact (`miniapp-smoke.spec.ts:97-99`), matching the "may skip only if em++ artifact unavailable" allowance.

### Residual risks
- The COOP/COEP/permissions-policy headers are enforced only by the test `static-server.mjs`; production static hosting must replicate them or cross-origin isolation (and thus audio) fails. Documented in `README.md`, but it's an operational dependency outside the artifact.
- `setInterval`-paced render-ahead (`audio.ts:55`) is timing-fragile under main-thread contention; underflow recovery is tested but real-device glitch behavior is unverified without hardware.
- Channel mismatch (Finding 2) is the main generic-ness hole against the "any conforming app" requirement.

### Verdict
**Not yet mergeable as "the static browser app works," but close.** The generic runtime, UI backend, MIDI/audio/persistence bridges, ABI, and boundary gates are correct, well-scoped, and honor the binding constraints (static-only, no app-specific logic, sysex multi-device MIDI, System-Default-only output, no `getUserMedia`, drag-suffix semantics, cross-origin gate). The blocker is Finding 1: the shipped entry point doesn't assemble the runtime, so "app open" is demonstrated only by test-side wiring while the tasks are marked complete. I'd gate merge on either implementing the `main.ts` composition root or explicitly re-scoping/unchecking the "app open" tasks, and I'd fix Finding 2 (or guard it) before claiming generic multi-channel support. Findings 3–5 are non-blocking follow-ups.
