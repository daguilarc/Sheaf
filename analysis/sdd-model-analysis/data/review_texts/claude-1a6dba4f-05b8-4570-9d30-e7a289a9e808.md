## Important

**I1 — Task 2 Step 5 "exactly one 1,024-point waveform command" per voice is unsafe as written (plan lines 305–306).**
The plan asserts *"each populated voice produces exactly one 1,024-point waveform command."* The rendering helper `BuildScopePolylines` **splits a waveform into multiple polylines at the transfer boundary**:
- `PortableUIBuilders.hpp:80–101` — a new polyline is started whenever `ScopePointCrossesTransfer(...)` is true.
- The existing test at `portable_ui_tests.cpp:389` literally asserts `structuralPolylines.size() == 2` ("structural reader splits at transfer sample").
- The real `AutoScope::CreateReader()` sets `hasTransfer_ = true` for a **locked** scope with a visible transfer region (`DspAutoScope.hpp:98–99`), which then makes `transferXSample_ < numXSamples` and forces a split into **two** `Polyline` commands totaling 1,024 points. Only when `hasTransfer_` is false (line 100–101, `transferXSample_ = numXSamples`) is there a single command.

So a populated, YIN-locked voice will commonly emit **two** waveform commands, not one. A Codex implementer following the plan literally would write `CountCommands(Polyline) == numPopulatedVoices`, hit a GREEN-gate failure, and have to debug/deviate. Note the design spec's own wording is correct and robust: spv-7 requires *"1,024 finite points ... in its copied color"* (design spec line 32; `synth-portable-visualizers/spec.md:32`), i.e. total point count, not command count. Existing tests already count total points via `RequirePolylinesInside`/`WaveformYChecksum` (`portable_ui_tests.cpp:132,162`) rather than asserting one command.
**Fix:** assert total finite in-bounds point count (= 1,024) across the voice's polyline command(s), one shared background+centerline, and empty-voice omission — drop "exactly one command."
