# Pre-Implementation Review: PolyAutoScopeVisualizer and Braid4 AutoScope Design

I read the design and verified its claims against `AppContext.hpp`, `AppConcepts.hpp`, `Engine.hpp`, `PortableUI.hpp`, `PortableUIBuilders.hpp`, `RuntimeMainComponent.hpp`, `runtime/Runtime.hpp`, `browser/BrowserRuntime.hpp`, `DspAutoScope.hpp`, `DspLogStructuredBuffer.hpp`, `ParameterModulation.hpp/.cpp`, and the Braid4 core/UI. Overall the architecture is well-matched to the existing code and most quantitative claims check out. There is one substantive threading-contract gap that blocks a clean PASS, plus several minor items.

---

## Critical

None.

## Important

### I1. `Reset()`/`PrepareToPlay` thread contract vs. registry dispatch is unspecified — potential consumer-vs-consumer data race

The AutoScope contract is explicit that **all** consumer operations share one thread: *"The UI thread owns ConsumePending, CreateReader, Reset, and direct AddSample/AddSamples calls. Do not mix direct UI ingestion with concurrent mutation from another thread."* (`DspAutoScope.hpp:18-24`). `Reset()` mutates the non-atomic consumer state `buffer_`, `diagnostics_`, `nextConsumerSequence_` (`DspAutoScope.hpp:271-289`); the registry drain (`ProcessUiFrame → ConsumePending`) mutates the same fields (`DspAutoScope.hpp:297-333`).

The design places the registry drain on the message thread (`Engine::MessageThreadTick`, `Engine.hpp:298-334`) and drawing on the message thread (`builder.Visualizer → visualizer->Draw()`, `PortableUIBuilders.hpp:454-459`) — those two are correctly co-threaded. But it also introduces a **new** consumer call, `PolyAutoScopeVisualizer::Reset()`, on the `PrepareToPlay` path (design §Lifecycle, lines 150-151; `Engine::Prepare → app_.PrepareToPlay`, `Engine.hpp:187-189`).

- At **startup** this is safe: `audioDeviceAboutToStart → Prepare → PrepareToPlay` runs synchronously *before* `startTimerHz` (`Runtime.hpp:294-296, 499-508`), so no timer tick can race it.
- For **message-thread-driven device switches** it is safe: the combo handler and the timer are both message-thread events, serialized.
- The gap: JUCE may invoke `audioDeviceAboutToStart` (hence `PrepareToPlay → Reset`) from an **OS-initiated device restart off the message thread**, concurrently with a timer-driven `MessageThreadTick` registry drain. That is two consumers mutating the same non-atomic AutoScope state → undefined behavior. The registry keeps ticking even when "DSP processing is stopped," so the design's "when DSP processing is stopped … safe prepare boundary" wording does not by itself remove the hazard.

Note this is a *new* interaction: today nothing in `PrepareToPlay` touches message-thread-only consumer state (Braid4's current `PrepareToPlay` at `Braid4Core.hpp:163-190` touches only DSP-owned state, which is protected by JUCE's audio-callback/prepare ordering, not by the message thread).

I flag the certain part with confidence — **the design does not state which thread `Reset()`/`PrepareToPlay` runs on relative to registry dispatch, nor add synchronization** — and the race itself as conditional on JUCE's restart threading (which I did not fully confirm). Recommended acceptance criterion: pin `Reset()` and registry dispatch to the same thread (e.g., require `PrepareToPlay`-driven resets to be marshaled to the message thread, or gate the registry tick during prepare), and add a test/assert that the two cannot run concurrently.

## Minor

### M1. `DrawVisible()` is `const` but must mutate owned scopes — ownership must use pointer indirection
The base contract is `std::vector<DrawCommand> DrawVisible() const` (`PortableUI.hpp:119-129`), yet `AutoScope::CreateReader` is non-const (`DspAutoScope.hpp:350`) and mutates the scope. The existing `AutoScopeVisualizer` sidesteps this by holding a non-owning `AutoScope*` (`PortableUIBuilders.hpp:345`). The design changes to **ownership** ("owns one address-stable AutoScope per voice"). Since AutoScope is non-copyable/non-movable, the implementation must hold scopes via `unique_ptr` (or heap pointer) so the const `DrawVisible()` can still reach a mutable pointee. Worth stating explicitly as an implementation constraint; otherwise a naive `std::vector<AutoScope>`-by-value member won't compile.

### M2. Registry/registrant destruction ordering is unstated
RAII unregistration is only stale-pointer-safe if the registry outlives every registrant. The registry is `Engine`-owned and the registrants live inside `app_` (also `Engine`-owned, `Engine.hpp:838`). The design should require the registry member to be declared **before** `app_` in `Engine` (so it is destroyed after `app_`), and state the destruction thread. Add an acceptance criterion for teardown order.

### M3. `AppContext` needs a new registry pointer + thread-role annotation
`AppContext` currently has no `UiFrameProcessorRegistry` field (`AppContext.hpp:80-103`), and its members carry binding thread-role comments. The design's new pointer must be wired in the `Engine` constructor before `app_.Init()` (like the other pointers at `Engine.hpp:72-84`) and documented with its thread role (message-thread register/dispatch). This is required plumbing the design implies but doesn't spell out; no concept change is needed (`AppConcepts.hpp` is unaffected).

### M4. "Without changing YIN evaluation diagnostics" has an overflow edge case
The test in design line 219 ("registry dispatch advances every voice's LSAB without changing YIN evaluation diagnostics") holds for `ConsumePending` in the normal path, but a producer gap larger than `transferCapacity` calls `InvalidatePhase()`, which zeroes `diagnostics_.phaseBase` (`DspAutoScope.hpp:302-307, 710-715`). The YIN *evaluation counters* (`evaluatedLevels/Lags/Pairs`, `confidence`, `detectionLevel`) are indeed untouched by a drain, but the assertion wording should scope itself to those counters and not "all diagnostics," or the overflow test will be flaky.

### M5. Cross-runtime "once per UI frame" is correct today but implicitly coupled to tick cadence
The claim that `MessageThreadTick` is the once-per-UI-frame boundary is verified: JUCE calls it per timer tick at `uiFrameHz` before the repaint hook (`Runtime.hpp:715-722`), and the browser calls it before `BuildUiFrame` (`BrowserRuntime.hpp:230-246`); `BuildTree` never dispatches the registry (`RuntimeMainComponent.hpp:91-123`), so resize/action rebuilds don't double-drain. This is sound. The only caveat worth noting in the spec: LSAB maintenance cadence is now bound to the message-tick cadence, which is shared with MIDI reconcile/patch-response work; if a future host ever ticked at a rate decoupled from paint, drain cadence would follow the tick, not the frame. Informational only.

## Verified claims (no action needed)

- **4× oversampling / 192 kHz producer rate**: confirmed (`kOversampleFactor = 4`, `internalSampleRate_ = sampleRate * 4`, `Braid4Core.hpp:27, 168`).
- **14-channel routing maps cleanly to existing modulation sources**: `rawMatrixOutputs_`(4), `rawLfoMatrixOutputs_`(4), `rawAudioStereoOutputs_`(2), `rawLfoStereoOutputs_`(2), and the two mono averages (`0.5*(L+R)`) all exist and are final by `Braid4Core.hpp:373-391`; groups already expose exactly two modulators each (`Braid4Core.hpp:288-323`), 4+2+1 twice = 14.
- **Modulator visualizer plumbing already exists**: `ModulatorMetadata.visualizer` (`ParameterModulation.hpp:200`) propagates to the modulation-depth parameter (`ParameterModulation.cpp:1193`) and into the cell's `std::atomic<Visualizer*>` (`ParameterModulation.cpp:779`), which Braid4's UI reads (`Braid4UI.hpp:63-77`) — no parallel draw path needed.
- **Tests to be replaced exist**: `braid4_modulator_visualizer_pointers_remain_null` and `braid4_modulation_view_remains_encoder_only_without_visualizers` assert the current null expectations (`braid4_system_tests.cpp:736, 758-771`).
- **Memory claims**: transfer = `262144 * (4+8) = 3 MiB`/scope (`DspAutoScope.hpp:47-49, 65`); ×14 = 42 MiB ✓. LSAB defaults 6×8192, 31-tap/0.09/5.0 (`DspLogStructuredBuffer.hpp:166-170`) ✓. 262144 @ 192 kHz ≈ 1.37 s ✓. `consumeBudget = 32768` comfortably exceeds ~6400 samples/frame/channel, so the drain keeps up ✓.
- **Registry dispatch is allocation-free**: dispatch calls only `ProcessUiFrame → ConsumePending → AddSample` into preallocated rings; the allocating `DrawVisible` is deliberately *not* on the dispatch path. Separation is coherent.
- **Realtime/UI separation**: `Writer::Push` is lock-free/audio-safe (`DspAutoScope.hpp:93-115, 724-737`) and touched only by the DSP thread; all consumer work is message-thread. Sound apart from I1.
- **Benchmark methodology** (warm-up excluded, command consumption to defeat DCE, deterministic signals, informational timing with deterministic work-bound assertions) is sound.

---

**Verdict: NOT PASS** — one Important finding (I1: unspecified thread contract for `Reset()`/`PrepareToPlay` relative to registry dispatch, with a conditional consumer-vs-consumer race) must be resolved with an explicit thread guarantee and acceptance criterion before implementation. The Minor items (M1–M5) are worth folding into the spec but are not blockers on their own.
