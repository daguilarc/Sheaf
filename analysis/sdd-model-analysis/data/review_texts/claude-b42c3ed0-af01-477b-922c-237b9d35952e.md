Scope confirmed: `FakeBrowserApp.hpp` audio/DSP path (`ProcessBlock`) is byte-for-byte unchanged — only UI wiring (`DrawInteractive`, `StatusText`, `uiWidth`/`uiHeight`) was added. No audio scheduling/DSP/ring/allocation changes anywhere in this diff.

### Findings, ordered by severity

**1. False-positive audio assertion — right channel never checked (Medium)**
`tests/audio-flow.spec.ts:89,94-95`. `SharedRingBuffer.create(2, 1024)` allocates a 2-channel bridge, but `SharedRingBuffer.write()` (`src/protocol.ts:52-67`) lays samples out **planar**, `base = channel * capacityFrames`. With `capacityFrames=1024`, channel 0 occupies flat indices `[0,1024)` and channel 1 occupies `[1024,2048)`. The test does `samples.slice(block*128, (block+1)*128)` for `block` 0–3, i.e. indices `[0,512)` — entirely inside channel 0. Channel 1 is never read or asserted. If the right channel were silent, NaN, or garbage, this test would still report "four finite non-silent audio blocks." Fix: also slice `[1024 + block*128, 1024 + (block+1)*128)` and assert on both channels.

**2. Missing cleanup in all four new "real WASM app" Playwright tests (Medium)**
`tests/fake-app.e2e.spec.ts` (`shell`, `gestures`, `narrow` tests) and `tests/miniapp-smoke.spec.ts` (`shell`, `gestures`, `narrow` tests) never call `app.stop()` or terminate the underlying `Worker`. Contrast with the sibling tests in `audio-flow.spec.ts:96-97` and `midi-flow.spec.ts` (`worker.terminate()` after `destroy`), and with the *removed* old `fake-app.e2e.spec.ts` code which explicitly called `state.audio.shutdown(); state.midi.stop(); await state.runtime.handle({ type: "destroy" })`. Playwright's per-test page teardown will kill the worker thread anyway, so this isn't a hard leak, but it's an inconsistent pattern within the same PR and drops the explicit destroy-path exercise (`runtime.handle({type:"destroy"})`) that used to be covered for these flows.

**3. Untracked generated screenshot artifacts, no `.gitignore` entry (Medium, hygiene)**
`tests/miniapp-smoke.spec.ts:112,180` write to `new URL("./screenshots/....png", import.meta.url)`, resolving to `projects/synth/browser/tests/screenshots/*.png`. `git status` shows this directory as untracked, and repo-root `.gitignore` only excludes `projects/synth/browser/test-results/` and `.../dist/`, not `tests/screenshots/`. As written, running this test suite once and then `git add -A` would commit binary screenshot diffs into the repo. Needs a `.gitignore` entry (or output should go under the already-ignored `test-results/`).

**4. Flaky-synchronization inconsistency between near-identical tests (Low-Medium)**
`tests/fake-app.e2e.spec.ts:139` uses a hard `await page.waitForTimeout(250);` before asserting on `observations.commands` (a functional assertion, not a visual one). The equivalent gesture test in `tests/miniapp-smoke.spec.ts:161-163` does the same check correctly with `await expect.poll(() => ...).toBeGreaterThanOrEqual(3);`. The hard-coded 250 ms sleep is a plain flake risk under CI load (too short) or needless slowness (too long) — should use the same `expect.poll` pattern as its sibling.

**5. Dead/misleading route bypass in both `installRealFakeApp` and `installRealMiniapp` (Low, correctness-of-comprehension)**
`tests/fake-app.e2e.spec.ts:26` and `tests/miniapp-smoke.spec.ts:32`:
```ts
await page.route("**/dist/src/main.js", (route) => {
  if (new URL(route.request().url()).search) return route.continue();
  return route.fulfill({ ... });
});
```
Verified against Playwright's actual glob-to-regex compiler (`resolveGlobToRegexPattern`): the pattern `**/dist/src/main.js` compiles to `^(.*/)dist/src/main\.js$`, anchored with no allowance for a trailing query string. `.../main.js?task5` does **not** match this pattern at all, so Playwright never invokes this route handler for the query-stringed dynamic import — the `if (search) return route.continue()` branch is unreachable dead code. The real module still loads correctly, but only because the route silently doesn't intercept it, not because of the explicit `continue()`. This will mislead the next person who touches these fixtures into thinking route interception is what's happening. Worth a comment or removing the dead branch.

**6. `worker.ts` dispatch-action duplicates the `call`/`callValue` pattern instead of reusing it (Low, maintainability)**
`src/worker.ts:285-291` manually does `requireModule()`/`requireHandle()` + inline status-check-and-throw, duplicating exactly what the existing `this.call()` helper (`src/worker.ts:327-330`) already does. Could be:
```ts
case "dispatch-action": {
  await this.call((module, handle) => module.dispatchAction(handle, command.name, command.value));
  const frame = await this.callValue((module, handle) => module.buildUiFrame(handle));
  return { type: "ui-frame", frame: Array.from(new Uint8Array(frame)) };
}
```
Purely stylistic; current code is correct.

**7. `offline` object in `midi-flow.spec.ts:302` mixes inverted boolean semantics under matching key names (Low, readability)**
`{ slotA: inputA.onmidimessage !== null, slotB: inputB.onmidimessage === null }` — `slotA` means "still bound," `slotB` means "became unbound," but both live under the same `{slotA, slotB}` shape used elsewhere (`boundAtStart`, `reconnected`) where both keys mean "is bound." The assertion is correct, but a future edit that "fixes" this to be consistently `!== null` would silently break the check without any type system or lint catching it. Consider inline comments or distinctly-named fields (e.g. `slotAStillBound`, `slotBWentOffline`).
