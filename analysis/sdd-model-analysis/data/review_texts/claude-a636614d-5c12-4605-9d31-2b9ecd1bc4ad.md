## Findings

### 1. [High] The only tests covering baseline preservation, real continuity retention, and search validity run in no aggregate/verification flow
`make test` (`Makefile:225`) includes neither `$(AUTOSCOPE_LAB_TEST_BIN)` nor the new `$(AUTOSCOPE_SEARCH_TEST_BIN)`. The search test is only reachable via the standalone `autoscope-search-test` target (`Makefile:120`), and neither the plan's Task 5 commit step (`plans/…-lab.md:449`, runs `build/autoscope_tests autoscope-lab-test` only) nor Task 6's full verification list (`:519-524`) invokes `autoscope-search-test`. Yet `autoscope_search_tests.cpp` is the sole home of: the pinned baseline-hash check (`:31`), the end-to-end AnalyzeDensity retention assertion on a real square wave (`:98-115`), and the search determinism/held-out-isolation checks (`:65-80`). Net effect: a regression in the user-visible A/B path — baseline drift, broken continuity retention, non-deterministic search, or holdout leakage — passes `make test` and every documented verification command. This is the highest-leverage gap: the A/B-confidence coverage exists but is effectively unhooked. Recommend adding both bins to `test:` (or at minimum adding `autoscope-search-test` to the Task 6 Step 6 list).

### 2. [Medium] Deterministic-search guardrails and held-out evaluation from Task 5 Step 5 are not implemented
Plan Step 5 (`:419-438`) and design §4 (`:225-229`) require the search to (a) refine only the top eight by adding viewport/alignment/history dimensions, (b) evaluate the top three on held-out cases, and (c) **automatically reject** candidates that worsen periodic truth error > 0.1 octave, double aperiodic false-alignment, create new empty frames, or fail deterministic replay. `Search.hpp:ScoreVariants` (`:147-199`) only ranks on training cases and sorts; there is no refinement driver, no held-out scoring pass, and no rejection logic. `StableRefinementCandidates` (`Search.hpp:93`) is defined but called by nothing except the test (`autoscope_search_tests.cpp:51`), and `SearchContinuity` (`:201`) never chains it. Because these are the guards that stop an overfit/regressing candidate from surfacing as an A/B option, their absence is a real overfitting-safety gap, not just missing polish. (Uncertainty: some of this may be intended for Task 6, but Task 5's stated interface list claims "deterministic coarse/local search," and the coarse-only half shipped without the local-refine/holdout/reject half.)

### 3. [Medium] Search scalar sums two different objective profiles across signals
`ScoreVariants` assigns each signal an objective by family (`UsesPeriodicObjective`, `Search.hpp:140-145`) and accumulates `periodic-lock` and `stable-general` scores into one `result.score` (`:185-189`). The design states a weighted scalar is used "only to rank a search **within a declared objective profile**" (`design…:210`); here a single ranking blends two profiles whose formulas differ (`Metrics.hpp:103-113`). `periodic-lock` carries an unbounded `octaveErrors` count (×0.05) and `stable-general` carries an unbounded `sourceSwitches+levelSwitches` count (×0.02); depending on corpus composition, the aggregate can be dominated by count terms from one family and mask periodic-lock differences. (Uncertainty: the normalized `p95RasterL1` is in [0,1] (`Metrics.hpp:75-77`), so per-frame terms are comparably scaled; the risk is concentrated in the unbounded count terms and in mixing objectives at all. Human A/B with raw components shown is the final gate, which mitigates but does not remove the ranking-validity concern.) Consider ranking under each declared profile separately (Pareto), as the plan's "score under periodic-lock and stable-general" more naturally reads.

### 4. [Low] Continuity memory is discarded on any frame whose recurrence challenger is invalid
In `ApplyDensityRecurrenceContinuity`, `DecideDensityRecurrenceContinuity` returns early when `!challenger.valid` (`DspAutoScope.hpp:1466`-ish), so `selected = challenger` (invalid) and the trailing state update sets `densityPreviousRecurrenceValid_ = false` (`:1521-1524`). Consequently the gate can only bridge *consecutive* frames that both carry a valid recurrence candidate; a single frame with no recurrence wipes the "previous family," even if activity still drives a coherent display. Whether this matches the design's "retain the previous recurrence family while it remains valid" (`design…:262-266`) is a judgment call — it's defensible (no recurrence ⇒ no family to retain) but may under-retain through brief recurrence dropouts on the very periodic-sine cases this feature targets. Flagging as a semantics question to confirm, not a proven defect. Only affects enabled (candidate) variants.

### 5. [Low] `frames.bin` grew 13 bytes/frame with no format-version bump and no non-default round-trip coverage
`EncodeFrames`/`DecodeFrames` insert the five continuity fields mid-record (`Archive.hpp:134-138`, `:197-201`). The pinned magic/version is unchanged, so old and new archives are indistinguishable by header — acceptable only because archives are ephemeral (design non-goal `:49`). More concretely: the archive round-trip test lives in the unchanged `autoscope_lab_tests.cpp`, so no test constructs a frame with non-default `continuity*` values and asserts they survive encode→decode. The search test's finiteness check (`autoscope_search_tests.cpp:91-96`) reads the in-memory `ExperimentResult`, bypassing `Encode/Decode` entirely. Low risk, but the serialized continuity data — which the blinded report depends on for the "retained/switched" overlay (`Report.hpp` `diag`, `:250`) — is currently unverified through the archive layer.

### 6. [Low/informational] `bestRecurrenceCandidate` trace now records the pre-continuity challenger, not the recurrence actually used
The trace assignment moved from post-continuity `bestRecurrence` to `recurrenceChallenger` (`DspAutoScope.hpp:2338-2343`), and `continuityChallengerCandidate` mirrors it. When retention fires, `bestRecurrenceCandidate` therefore points at the *rejected* challenger while the retained slot only appears via `selectedCandidate` + `continuityRetainedPrevious`. This is internally consistent and the search test relies on `selectedCandidate != continuityChallengerCandidate` (`autoscope_search_tests.cpp:114`), but the field name "best recurrence candidate" is now misleading for anyone reading a trace/report expecting it to name the recurrence that drove the span. Worth a comment or a rename to `bestRecurrenceChallengerCandidate`.
