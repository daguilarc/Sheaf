## Findings (most severe first)

### Critical
None.

### Important

**1. `HandleSetAbsolute` allocates on the audio thread and can `std::terminate` it — the sibling `HandleIncDec` does neither.** `ParameterModulation.cpp:1528, 62–63, 123–124, 185`; throws at `1536, 1542, 45, 56, 89`.

- `uiBus_.Process()` runs **inside the audio callback** (`Engine.hpp:263`, immediately before `app_.ProcessBlock`; `AppContext.hpp:83` documents `uiBus` as "consumer: audio thread"). So `MessageInBus::Apply → …→ Parameter::HandleSetAbsolute` executes on the RT audio thread for every absolute CC.
- `BuildAbsoluteEditLocations` returns a heap `std::vector` (`reserve`+`push_back`) and `ProjectAbsoluteTarget` allocates three more (`std::vector<double>`, `std::vector<bool>`, `std::vector<float>`). The relative sibling `HandleIncDec` is allocation-free (verified). A physical absolute encoder emits a *stream* of CCs during a sweep, so this is per-message heap traffic in the audio callback. Sizes are bounded (`≤ 2 + 2·64 = 130`) and `HandleSetAbsolute` already uses a stack `std::array` for `gestureContributions` — the same fixed-capacity pattern trivially applies to `locations` and the solver scratch.
- The comment at `1530` calls the three `throw`s "unreachable for valid Parameter-owned normalized storage." That precondition is **not guaranteed**: patch load writes `SceneCenter`/`GestureValue` straight from JSON with no clamp (`ParameterModulation.cpp:1303, 1323`). A patch carrying a latent value outside `[0,1]` makes `ProjectAbsoluteTarget` return `false` (its in-range storage guard) → `throw std::logic_error` → propagates out of the audio callback (no `try/catch` around `uiBus_.Process`) → `std::terminate`. The engine otherwise *tolerates* out-of-range latent storage (it clamps only at `ComputeAtDepth`), so the absolute path is the sole code that converts tolerable data into a process crash.

*Uncertainty / precedent, stated plainly:* audio-thread `std::vector` allocation already exists on this exact path (`Bank::ApplyModifierToTopLevel`, `ParameterModulation.cpp:2492/2494`), and throwing on this path already exists (`ValidateSceneEndpoints` in `HandleIncDec`). So neither facet is strictly novel, and a maintainer may consciously accept them. But `Engine.hpp:236–237` explicitly frames non-RT work on the audio path as requiring a *"sanctioned … non-RT exception,"* and this change adds an unsanctioned one that fires far more frequently (per encoder tick) than the bank-select precedent. Recommend: fixed-capacity stack buffers, and replace the three `throw`s with a graceful early return (matching `HandleSetAbsolute`'s own non-finite early-return at `1483`) and/or clamp latent storage on patch load. This is not waivable as polish; it should be fixed or explicitly signed off.

### Minor

Present-but-null `mode` fails the whole encoder-config load even when a valid legacy `relativeMode` exists.** `MidiController.cpp` `FromJSON(EncoderMidiInConfig)`: `ObjectHasKey(json,"mode")` treats a `null` `mode` as present → authoritative → `FromJSON(null)` fails → entire config load fails (tested at `encoder_mode_json_new_field_is_authoritative`). Defensible as "new field is authoritative," but a `null` new field falling back to a valid legacy field would be friendlier and still spec-consistent. **3. `UISystemMessage::ParamSetAbsolute` is exposed as a selectable *system-button* press action** (`MidiConfigViewModel.cpp` catalog + `PressForUISystemMessage` → `ParamSetAbsolute(…, previous.press.value)`, default `0`). A momentary button emitting a fixed absolute value is semantically odd, but it exactly parallels the pre-existing `ParamPush`/`ParamIncDec` catalog entries and round-trips correctly. Consistency argues for keeping it; noted only for awareness.
