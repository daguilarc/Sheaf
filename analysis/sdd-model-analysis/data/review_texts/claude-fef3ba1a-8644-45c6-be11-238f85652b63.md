## Residual implementation risks (non-blocking)

1. **"Monotonic sample index" attribution is imprecise** — `design.md:148-149` says the worker "advances the monotonic sample index by that worker block size." In the real engine, `Engine::ProcessBlock` owns that: it advances `sampleCounter_` internally (`Engine.hpp:268-270`) and sets `block.startSample`. The host's actual per-call obligation is a *separate* wall-clock `timestamp` argument used for message-bus scheduling — the JUCE runtime passes `NowMicros()` (`Runtime.hpp:496`), not a sample count. An implementer reading D4 literally could conflate `startSample` with the `timestamp` param or double-advance. sar-24's "preserve monotonic sample-position semantics" is satisfied automatically as long as `block.numFrames` equals the negotiated block; worth a one-line clarification at implementation time.

2. **Drag-delta encoding is a JUCE-backend detail not surfaced portably** — the "replacement-delta" semantics the spec requires (sbw-9, sru-22, task 3.3) are implemented in `PortableJuceBackend.hpp` as string-surgery on the action value: replace everything after the last `:` with the current delta (commit `a318847f`, lines ~509-529). This colon-delimited protocol isn't expressed in the portable `Action`/`pointerDragAction` layer, so the browser backend must reproduce the exact suffix convention. The spec captures the *intent* correctly but not the encoding; mismatch here would silently break encoder gestures and Playwright would need to assert the concrete value format.

3. **Reconcile-core reuse is not mandated** — a JUCE-free reconcile core already exists (`MidiReconcile.hpp` — `PlanMidiReconciliation`/`ExecuteReconcilePlan`), which the browser MIDI bridge could reuse directly. sbw-5/D5 require only "desktop-equivalent semantics," not reuse. Reimplementing reconcile logic in JS/TS instead of driving the existing core risks behavioral divergence from desktop; consider tightening the design toward reuse.

4. **Whole-frame command buffers** — D6/risks explicitly defer incremental optimization; acceptable but flagged as known perf debt.

None of these block the proposal. The specs, design, tasks, and proposal are internally consistent and faithful to the existing engine/runtime/UI contracts.
