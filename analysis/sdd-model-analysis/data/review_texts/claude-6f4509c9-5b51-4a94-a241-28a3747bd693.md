## Review: Task 4 — Braid4 Adoption (`decdbadd..108d2e81`)

### Important

**1. The generic `Parameter` sparse-depth hot-path optimization has no OpenSpec authorization or documentation.**
`ApplyMaterializedModulation` (projects/synth/src/ParameterModulation.cpp:1511-1517, declared at include/synth/ParameterModulation.hpp:456) and `materializedModulationIndexes_` (ParameterModulation.hpp:485) change the evaluation strategy of the shared, application-agnostic `Parameter` class used by every synth app, not just Braid4. Grepping `openspec/changes/add-standard-modulators/` (proposal.md, design.md, tasks.md, and all four delta specs) turns up zero mentions of "sparse," "materialized," or a hot-path optimization — the only "authorization" for this exists as a paragraph in `.superpowers/sdd/task-4-standard-modulators-report.md`. Per the project's own spec-first discipline (design.md's Risks section documents even minor tradeoffs like reserve/allocation, but not this), a core-class algorithmic change of this magnitude should have a corresponding design decision and/or a `synth-parameter-modulation` delta requirement describing the sparse/dense-equivalence contract, so future maintainers of `Parameter` know this invariant exists and must be preserved. As implemented it's a silent, spec-invisible change to shared infrastructure justified only in prose inside an implementation report.

**2. The committed report under-discloses a real 96 kHz deadline miss.**
`.superpowers/sdd/task-4-standard-modulators-report.md`'s "Concerns" section only reports a 48 kHz p99 outlier (4.608 ms) from the implementer's own final-verification pass. It does not mention the more severe 96 kHz miss the controller observed independently (avg 1.461 ms, **p99 3.592 ms** — the 96 kHz p99 threshold is `blockSeconds * 0.80 ≈ 2.133 ms`, so this run missed by ~68%, not just noise). Three reruns then passed cleanly (1.513/1.518/1.752 ms), and thresholds were genuinely not relaxed (`braid4_deadline_tests.cpp` diff only reorders the `std::cout` print before the same `0.60`/`0.80` assertions — values unchanged). So: **thresholds are honestly preserved, but compliance is only probabilistic, not deterministic**, and the shipped report doesn't capture the worst observed evidence. That gap matters for anyone relying on the report as the record of task quality.

**3. The new hot path adds avoidable per-element overhead that eats into the already-thin margin.**
`ApplyMaterializedModulation` (ParameterModulation.cpp:1511-1517) calls `group_.GetModulators().Value(voiceIx, modIx)` per materialized index, which routes through `Modulators::Value` → `Modulators::Index` (ParameterModulation.cpp:316-324, two branchy bounds checks) → `std::vector::at()` (another bounds check). `voiceIx` and `modIx` are already guaranteed in-range by the caller (`GetRaw`/`TargetValue` validate `voiceIx`; `modIx` is drawn from `materializedModulationIndexes_`, which is bounded by construction). The pre-change `Modulators::Apply` (ParameterModulation.cpp:256-269) did one bounds check up front and then unchecked array indexing in the loop — strictly cheaper per iteration. Given findings #2's evidence that 96 kHz margin is tight enough to intermittently miss, removing this redundant checking (e.g., a raw-pointer/index accessor into `values_`) is a concrete, low-risk way to buy back headroom rather than relying on "it usually passes."

Low risk since the code path is identical (`if (parameter != nullptr)` is the only guard), but it's an easy gap to close.
