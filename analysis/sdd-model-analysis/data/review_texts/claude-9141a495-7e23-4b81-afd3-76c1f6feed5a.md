## Browser/Wasm synth runtime review — `add-browser-wasm-synth-runtime`

### HIGH

**1. Heap allocation on the AudioWorklet realtime thread (violates sbw-3).**
`sheaf_browser_process` is the Emscripten worklet render callback (`ProcessBrowserAudio` → `sheaf_browser_process`, `BrowserMiniAppHost.cpp:207-247, 350-366`). Inside it, `DrainUiActions` (`BrowserMiniAppHost.cpp:117-127`, called at `:361`) does:

```cpp
state.engine->Application().PortableSurface().DispatchAction(
    synth::ui::Action::WithValue(action.actionName, action.value));
```

`synth::ui::Action` holds `std::string name`/`std::string value` and `WithValue(std::string, std::string)` takes them by value (`PortableUI.hpp:59-65`), so each queued UI action constructs two `std::string`s → heap allocation **on the audio render callback**. `DispatchAction` then runs `DispatchMiniAppAction` and pushes `MessageIn` onto `uiBus_` (`MiniAppUI.hpp:121-145`). sbw-3’s "Realtime callback avoids… string logging, or unbounded allocation" scenario forbids exactly this. It only fires when the user interacts, but it is still `malloc` on the RT thread. The design (Decision 5) intends the worklet to drain into the UI bus, but the concrete path here is not allocation-free — actions should cross as fixed-size PODs and be converted without constructing `std::string` on the audio thread (e.g. dispatch via `string_view`/preallocated storage, or move the action→MessageIn translation onto the main thread and only pass POD `MessageIn` through the queue).

Note also `DrainUiActions` runs the `uiBus_` **producer** on the audio thread, whereas the native/JUCE design has the message thread as producer and the audio thread as the consumer (`Engine::ProcessBlock` → `uiBus_.Process`, `Engine.hpp:263`). Same-thread push+pop is race-free for the queue itself, but any direct view-model mutation inside `DispatchMiniAppAction` that `BuildTree()` (main thread, `RefreshUiFrame`) also reads would be a cross-thread hazard. I confirmed the basic miniapp actions only push value-type `MessageIn` (`MiniAppUiModel.hpp:380-455`), so I did not find a concrete state race here — but I could not exhaustively verify every action branch (patch/MIDI-name actions), so I flag it as needing confirmation.

### MEDIUM

**2. sbw-10 "Browser smoke checks persistence" is not actually covered in Chrome.**
The only Playwright/Chrome test is `tests/smoke/audio-smoke.mjs` (audio telemetry + nonblank canvas). Storage round-trips are tested only against an in-memory JS fake (`tests/storage.test.mjs:29 fakeModule()`), and MIDI-unavailable only against a stub navigator in node (`tests/smoke/midi-unavailable-smoke.mjs`). No test exercises a real IDBFS save → reload → read-back in Chrome, nor the C++ engine’s patch persistence over the `/sheaf` mount. sbw-10’s persistence scenario ("a reload can read the saved data back from browser storage") and the in-Chrome MIDI-status scenario are therefore unmet, and tasks 7.2/7.3 overstate coverage (they’re node-level, not Chrome smoke). The storage helpers are well-tested in isolation, but the end-to-end IDBFS path isn’t.

**3. Outgoing MIDI ignores endpoint selection (partial sbw-5).**
`MidiMessage` carries no port id (`BrowserHostTypes.hpp:54-59`) and the single `BrowserMidiOutputSink` is bound to sink 0 (`BrowserMiniAppHost.cpp:329`). On the JS side, `drainOutput` routes every drained message to `defaultOutputPortId()` = the first output port (`midi.js:223-244`). sbw-5 requires sending "through **selected** browser output ports." For a single-output miniapp this is functionally fine, but device selection is not honored, and multiple outputs would all collapse to port 0. Worth calling out as a v1 limitation vs. the spec wording.

### LOW / observations

**4. Two parallel audio implementations; the hand-written one is dead in production.** `js/worklet-processor.js` (`registerProcessor("sheaf-synth")`) plus `runtime.js:buildWorkletInitMessage` implement a hand-written worklet that copies from scratch buffers via `sheaf_browser_audio_output_buffer/_channel`. Production boot instead uses the Emscripten Wasm Audio Worklet (`sheaf_browser_start_audio` → `emscripten_create_wasm_audio_worklet_node`, registered `"sheaf-browser-synth"`). `boot.js` never `addModule`s `worklet-processor.js`; it’s exercised only by its unit test. The `_sheaf_browser_audio_output_buffer/channel` exports exist solely for this unused path. This is a maintenance/clarity hazard — two audio paths that can drift. (The production Emscripten path does appear to satisfy sbw-1’s "compiled module, not SINGLE_FILE": `instantiateWasm` reuses the `WebAssembly.compile`d module and WASM_WORKERS shares it to the worklet — no `SINGLE_FILE` in the Makefile.)

**5. C++ `BrowserStatus`/`BrowserStatusCode` machinery is disconnected from JS.** `sheaf_browser_status` is not wrapped in `createBrowserHostExports` and never read by JS; status codes like `MissingSharedArrayBuffer`, `MidiUnavailable`, `StorageFailed` are computed in C++ but never surfaced. JS recomputes its own status independently (`runtime.js` `assertSharedMemorySupport`, `midi.js`). Meanwhile `sheaf_browser_process` writes `state.status` every audio block (`BrowserMiniAppHost.cpp:364`) concurrently with main-thread writers — a benign data race (non-atomic struct, no reader), but pointless churn on the RT thread and dead surface area.

**6. `sheaf_browser_log_record` is a no-op stub (`BrowserMiniAppHost.cpp:471-473`).** The worklet→main log queue that sbw-7/sbw-8 ("logs avoid realtime work") describe isn’t implemented; it’s vacuously satisfied only because the worklet never emits logs. Fine for v1 but the requirement’s queue is not real.

**7. MIDI access is requested automatically at page load** (`boot.js:397-399`) with `{ sysex: true }`, i.e. a sysex permission prompt fires without a user gesture. Not a spec violation (sbw-2’s activation gate is about *audio*, and audio is correctly gated behind the Start click — `sheaf_browser_start_audio` runs synchronously in the click handler before any `await`), but prompting for sysex on load is an aggressive UX default.

**8. Smoke launches Chrome with `--autoplay-policy=no-user-gesture-required`** (`audio-smoke.mjs:20`). It still clicks `#start-audio`, but the flag means the smoke would pass even if the activation gate regressed, weakening sbw-2 validation.

**9. `frame.header.dirty` is always true.** `RefreshUiFrame` calls `SerializeFrame(..., /*dirty=*/true)` unconditionally (`BrowserMiniAppHost.cpp:156`), so `runtime.js:92`’s `frame.header.dirty` check is inert; change detection relies solely on version dedup. Harmless but the dirty flag is meaningless.

### Things that check out
- Negotiated audio values (sbw-3): `sheaf_browser_prepare` uses `emscripten_audio_context_sample_rate` and a 128-frame quantum (`BrowserMiniAppHost.cpp:513-515`). ✓
- v1 audio-input deferral (sbw-4): `AudioInputSupportStatus` keys off `MiniApp::Config().numAudioInputs`, no `getUserMedia` anywhere; worklet is output-only (`numberOfInputs = 0`). ✓
- Isolation headers (sbw-9): static preview and `_headers` both set COOP `same-origin` / COEP `require-corp` / CORP / `Permissions-Policy: midi=(self)`, and the shell smoke asserts them (`static-preview.mjs:14-32`, `browser-shell-smoke.mjs:16-19`). ✓
- Shared-memory gate (sbw-7): `assertSharedMemorySupport` requires `SharedArrayBuffer` + `crossOriginIsolated`, diagnosed before engine start with no silent fallback (`runtime.js:10-18`, `boot.js:295-299`). ✓
- Storage confinement/ordering (sbw-8): root pinned to `/sheaf`, `assertRootConfinedName` blocks traversal, `comparePatchVersionNames` gives deterministic ordering, initial `syncfs(populate)` before `sheaf_browser_create` and post-write sync off the RT path (`storage.js`, `boot.js:317-328`). ✓
- Ordering in the audio callback matches sbw-7: drain UI + MIDI queues, then `ProcessBlock` (`BrowserMiniAppHost.cpp:361-363`). ✓

The single finding I'd treat as blocking is **#1** (RT-thread allocation), with **#2/#3** as spec-completeness gaps to resolve before archiving. I did not run any builds or tests (read-only review); the allocation claim rests on `Action`/`WithValue` using `std::string`, which I verified at `PortableUI.hpp:59-65`.
