**1. [Medium — latent, pre-existing, not introduced by this diff] Order of operations in `LaunchRegisteredApp` can leave the window's content pointer dangling if a second session is ever launched.** `projects/synth/apps/sheaf-patch/Main.cpp:74-85`

```cpp
auto session = synth_runtime::MakeRuntimeSessionOwner<App>(std::move(paths));
const synth::RuntimeConfig config = App::Config();
window_->setName(juce::String(config.appName));
activeSession_ = std::move(session);                                    // <-- destroys old activeSession_ first
window_->ShowContent(activeSession_->Component(), config.uiWidth, config.uiHeight);  // <-- window still pointed at old (now-destroyed) component until this line
```

`window_->ShowContent` uses `setContentNonOwned(&component, false)` (Main.cpp:64), so `DocumentWindow`/`ResizableWindow` holds a raw, non-owning pointer to whatever component was last shown. If `activeSession_` already holds a session when this function runs again, `activeSession_ = std::move(session)` destroys the previous `RuntimeSessionOwnerFor<App>` — and with it the previous `ShellComponent<App>` — while `window_`'s content pointer still references that just-destroyed component, until the very next line repoints it. That's a real dangling-pointer window, not just a style nit.

This exact ordering already existed pre-Task-7 (`miniappSession_ = std::move(session); window_->ShowContent(miniappSession_->Component(), ...)`), so it is *not* a regression introduced here, and today it's unreachable: there's no "back to launcher" / relaunch UI path, so `LaunchRegisteredApp` can only ever run once per process with `activeSession_` starting null. But Task 7's stated purpose is to generalize this into a path that supports multiple registered apps (Task 8 adds Dresden), and once a second registration or a return-to-launcher path exists, this becomes a live use-after-free risk. Worth fixing now while the code is being touched, by reordering so the window is repointed at the new component *before* the old session is released, e.g.:

```cpp
auto session = synth_runtime::MakeRuntimeSessionOwner<App>(std::move(paths));
const synth::RuntimeConfig config = App::Config();
window_->setName(juce::String(config.appName));
window_->ShowContent(session->Component(), config.uiWidth, config.uiHeight);
activeSession_ = std::move(session);
```

Not a blocker for this task (behavior is unchanged from before, and the brief doesn't ask for multi-launch safety), but flagging per the review's explicit ask about this lifetime pattern, and recommend addressing before/alongside Task 8 rather than carrying it forward silently.
