### Findings (by severity)

**1. [Important — correctness / spec conformance] Matrix→parameter feedback is delayed two internal samples, not the spec-required one; the passing test masks it.**

- `Dresden4Core.hpp:231-261` (`ProcessInternalSubframe`) calls `ProcessParameters(internalIndex)` **before** `quadGroup_->UpdateModValues()`.
- `ProcessParameters` is what bakes modulation into `currentKnobValues_` (via `ProcessLite`→`GetRaw`, `ParameterModulation.cpp:1030-1032, 811-817`), and that is exactly what the VCO reads through `GetLinear`→`CachedKnobValue`. `UpdateModValues()` only stages `modulators_.values_`; it does **not** retroactively update `currentKnobValues_`.
- Consequence: a matrix output published at internal sample `n` (`Dresden4Core.hpp:250-254`) is loaded into `values_` by `UpdateModValues` at the top of subframe `n+1`, but is not *evaluated* by `ProcessParameters` until subframe `n+2`. So matrix feedback reaches parameter evaluation after **two** internal samples.
- Spec requires one: `specs/synth-dresden-4/spec.md:189` ("matrix feedback **reaches parameter evaluation after exactly one internal sample**") and the scenario at `:82-86` ("sample n+1 is the first sample that consumes the new matrix value"). Task 5.4 is checked as verifying this.
- Why the test doesn't catch it: `dresden4_system_tests.cpp:414-416` asserts the delta only at the `UpdateModValues` **bookkeeping** boundary (`lastConsumedMatrixOutputPublicationInternalIndex == lastInternalSampleIndex - 1`), i.e. that `UpdateModValues(n)` reads publication `n-1`. It never asserts when parameter *evaluation* first sees the new value.
- The plan's own documented process order is correct and would satisfy the spec: Task 5, Step 5 — "…update normalized matrix sources, `UpdateModValues(quadGroup)`, advance scope" places `UpdateModValues` at the **end** of the subframe, matching MiniApp (`MiniAppCore.hpp:214`, where the LFO source is produced *before* the end-of-frame `UpdateModValues`, yielding a true 1-sample delay).

  **Fix:** move `quadGroup_->UpdateModValues()` to the end of `ProcessInternalSubframe` (after `normalizedMatrixSources_` is published), and re-target the delay assertion to the parameter-evaluation path rather than the `UpdateModValues` boundary. *Alternatively*, if the 2-sample behavior is actually intended, amend spec d4-8 and the test so the requirement matches reality — right now spec, test, and implementation disagree.

  **Practical impact is negligible** (one extra internal sample ≈ 0.25 host samples, sub-microsecond, inaudible; the loop stays stable and allocation-free; feedback is only audible when a user routes matrix depth into a quad parameter). This is flagged because it is an explicit requirement in exactly the area I was asked to scrutinize, it is checked off as verified, and the guard test validates the wrong invariant.

**2. [Minor — non-blocking, test robustness] 96 kHz average-CPU deadline test has near-zero margin and flakes under load.**

- `dresden4_deadline_tests.cpp:196` (`avg <= block * 0.25`). Per-block work (256 host frames × 4 internal subframes) is host-rate-independent, so 96 kHz CPU% is ~2× the 48 kHz figure and lands right at the 25% ceiling (48 kHz measured ~12.5%). It **failed once** during my run (avg 0.666 ms vs 0.667 ms limit) while the machine was loaded from a concurrent build, then passed **12/12** on an idle machine. Not a Dresden correctness bug, but the threshold leaves so little headroom that it will flake on loaded or slower CI runners. Consider a small margin or a documented quiet-runner precondition.
