## Verdict: No blocking issues

The implementation faithfully realizes the accepted spec deltas across all six functional task groups. The patch/config separation, runtime-owned data paths, in-app browser, and Back-save policy are all correctly wired, and the test suite covers the specced scenarios directly.

### Regression/blocker checks (all pass)

- **Patch/config separation (spp-2, spp-4, sar-8)** — `BuildPatchJSON` writes only `schema`/`schemaVersion`/`patchName`/`parameterValues` and explicitly `(void)`s the MIDI/audio args (`PatchPersistence.cpp:264-277`); `LoadPatchJSON` and `ApplyPatchMessage` are parameter-only; `ValidatePatchJSON` tolerates but ignores legacy sections. Engine's audio-device-changed / MIDI-rebuild-on-patch machinery is fully removed, so patch load/revert cannot touch instrument or audio state. Covered by `engine_tick_preserves_audio_device_when_patch_load_has_legacy_audio_section`.
- **Runtime-owned data paths (sar-17)** — `RuntimeDataPaths::FromDataRoot` derives `patches/`/`logs/`/`config.json`; `Runtime::DefaultDataPathsForApp` resolves `userApplicationDataDirectory/Sheaf/<appName>` (`Runtime.hpp:156-163`); `SetRuntimeDataPathsForTesting` injects scratch paths. Removed fields (`patchesRoot`/`logsRoot`/`preferred*DeviceName`) are gone from `RuntimeConfig` and `MiniAppCore`; grep confirms no stale references remain.
- **Config load ordering (sar-18, slog-7)** — `Engine::Initialize` loads config after app `Init`/default-snapshot and before `RebuildMidiProcessors`, and `Runtime::Start` runs `StartupReconcile`/device-open after `Initialize`, then seeds the output/input device from `AudioDeviceSnapshot`. Log directory is configured before the first drain. Ordering is proven by `engine_initialize_loads_runtime_config_before_midi_processors_and_then_startup_patch` and the missing/invalid-config cases.
- **In-app browser replaces OS chooser (sru-6, sru-13)** — `FilePage` uses `synth::PatchBrowser`; no `juce::FileChooser` anywhere. Root-escape rejection (absolute, `..`, symlink) is enforced by `IsSafeRelativePath` + canonicalized `IsExistingDirectoryUnderRoot`, tested by `patch_browser_rejects_root_escape_paths`. Deterministic listing tested.
- **Back-saves-config policy (sru-12)** — `RuntimePagePolicy` gates Audio/Controllers only; `MainPane::ReturnFromPage` calls `SaveRuntimeConfiguration()` accordingly; File Back does not. Covered at both the pure-policy level (`contract_tests.cpp:148`) and the engine level (`engine_runtime_page_back_policy_saves_config_for_audio_and_controllers_only`).
- **Startup latest-patch tie-break (sar-8)** — `LatestPatchDirectory` (`Engine.hpp:648-653`) selects greatest version filename, ties broken by directory name — exactly as specced.
- **Docs/tasks (7.x)** — Both READMEs describe the data root, `patches/`/`logs/`/`config.json`, in-app browser, and Back-save behavior; task list is fully checked and consistent with the code.

### Low nits (non-blocking, no action required for sign-off)

1. **Stale future-tense comments in `Engine.hpp`** — the `audioDeviceState_`/`lastNotifiedAudioDeviceState_`/`SetAudioDeviceChangedCallback` member comments still say config loading "will seed it in a later task" / "when Task 4 wires persisted audio settings" (`Engine.hpp:~528-563`), but `LoadRuntimeConfiguration()` already does this in the same file. Cosmetic; the code is correct.

2. **Save As pre-fills the current patch name** — `FilePage::BeginBrowser` seeds `saveNameEditor_` with the current patch's directory name (`FilePage.hpp:230-234`). Because `ResolveSaveAsPath` permits an existing directory and `PatchManager::SavePatchAs` then returns `AlreadyExists`, a user who accepts the pre-filled name on Save As gets a no-op (logged). This is consistent with the spec (Save is the update path; Save As creates a new directory), just mildly awkward UX.

Both are minor and can be batched into a future cleanup. The change is ready for archive.
