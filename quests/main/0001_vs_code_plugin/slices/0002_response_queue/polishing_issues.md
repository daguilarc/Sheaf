- title: Response queue can send queued responses before tool outputs
- details: `RealtimeAgentSessionImpl.HandleIncomingEvent()` currently calls `m_responseQueue.OnIncomingEvent(event)` before `HandleToolCallExtraction(event)`. For a `response.done` that contains function calls, `ResponseQueue.OnIncomingEvent()` clears the active response and drains any caller-queued response-affecting units immediately. If a caller queued `sendTextMessage(..., { createResponse: true })`, `sendStructuredContext(..., { createResponse: true })`, or `createResponse()` while the model was producing the function call, that queued unit can transmit its `response.create` before the `ToolDispatcher` sends the `function_call_output` for the just-finished model tool call. This violates Spec 02's required sequence that tool results are sent back as `function_call_output` and then another model response is requested, and it can cause the model to continue without seeing the tool result or with conversation items in the wrong order. This path is not covered by the current response queue tests, which only cover tool follow-up ordering when no external queued response is waiting.

  To mark this issue `completed`, the implementation must guarantee that tool outputs extracted from the terminal model response are transmitted before any newly unblocked response creates can run, and the tool follow-up `response.create` must still route through the same queue. Add focused coverage for a terminal `response.done` containing a function call while at least one external response-affecting unit is already queued, asserting that the sent order puts `function_call_output` before any subsequent `response.create`.

  Re-check after the polisher's `Fixed` response at 2026-05-23T21:18:40Z: the added hold mechanism resolves only the case where a function call is first extracted from the terminal `response.done`. The implementation still dispatches tool calls earlier from `response.function_call_arguments.done`; those calls are added to `m_dispatchedCallIds` before the terminal `response.done`. When that later `response.done` arrives, `ReserveToolOutputHolds()` either sees no function call in `response.output` or skips the call because it is already in `m_dispatchedCallIds`, so no pending tool-output hold is registered. If the tool callback is still running and an external response-affecting unit is queued, `m_responseQueue.OnIncomingEvent(response.done)` can still clear active state and drain the external queued message/`response.create` before the delayed `function_call_output` is transmitted. To close this issue, the fix must also cover tool calls dispatched from streaming argument completion events that have not yet emitted their `function_call_output`, with a test that queues an external response-affecting unit while the response is active, receives `response.function_call_arguments.done`, then receives terminal `response.done` before the async tool output is sent, and asserts the tool output still precedes any external message or `response.create`.
- resolution_notes: Verified the follow-up fix. `ReserveToolOutputHolds()` now registers pending tool-output holds for both terminal `response.done` function calls and streaming `response.function_call_arguments.done` events, and it keys the skip condition off emitted tool outputs rather than dispatched tool calls. `TransmitOutgoing()` records outgoing `function_call_output` events and notifies the queue after the socket send, so draining queued response-affecting units happens only after the tool output is actually transmitted. The added tests cover both the terminal `response.done` extraction path and the streaming argument-completion path where `response.done` arrives before a slow async tool emits output. The issue is resolved.
